# 程序的语义退出与融合方案审查（精简计划）

本次调整程序退出条件和融合方案审查，并补充 stage3 的方案选择记录及其传递。其他流程、失败处理、提升/退步达到 5% 时的 knowledge 记录和最大迭代上限保持不变。本版为已确认并落实的方案，不展开代码实现。

详细说明和实例依据见[完整版](<workflow_fusion_selection_semantic_exit_design_full.md>)。

三个性能判断的代码现状及后续建议，见[性能判断规则](workflow_performance_decision_rules.md)。

## 前提：记录性能最好的实现

程序在有效性能评测完成后，记录对应的算子实现方案、融合方案、HAP、avg_speedup、性能报告地址和算子实现文件夹路径。代码必须与成绩对应；未完成有效性能评测的实现不参与最优选择。

入库前须通过正确性验证，包括下述连续调用自测，并采用当前统一的性能评测口径。计时有疑问或口径不同的历史成绩不能直接入库，须重新验证；只通过已有 case，不能证明缓存复用逻辑正确。

选择标准：精度通过且全部 case 达标的实现优先，再按 avg_speedup 选最优。HAP 保留用于分析。

## 场景1：每个 case 的 speedup 都 ≥ 1

此时不立即退出，继续优化。

如果 x 次有效性能迭代的累计提升小于 5%，程序选择已记录的最佳达标实现，交给 stage10 总结，退出迭代。x 在配置文件中设置。

尚未满足退出条件时，保留 stage6 → stage9 → stage3 → 下一轮 stage4。stage9 根据性能和瓶颈提出优化建议，不再因为方案不是单 kernel，就强制继续提高融合程度。

本轮全部 case 达标但平均加速比退步达到 5% 时，stage9 先记录退步教训，程序再恢复最佳达标代码，stage3 从最佳基线继续改；若本轮同时满足语义退出，也先记教训再交付最佳版本。

## 场景2：并非每个 case 的 speedup 都 ≥ 1

保留 stage6 → stage7 → stage8 → stage9 → stage3 的原流程。

本轮仍有慢 case 时，即使平均加速比退步达到 5%，也只记录退步教训，保留当前实现继续优化，不自动恢复历史最佳代码。

stage9 结合 stage7 的瓶颈分析、stage8 的优化建议和 stage3 的《融合方案选择决策依据.md》，同时查看各未达标 case 的历史 speedup、距 1 的差距及改善趋势，动态决定继续当前方案做局部优化，还是更换融合方案。修改意见仍使用 P0/P1/P2。

如果连续 y 次有效性能迭代的累计提升小于 5%，stage9 重点重新比较已输入的 JSON 融合算子库及概率。y 在配置文件中设置；停滞触发审查，不直接强制换方案。即使平均提升不足 5%，若可信评测显示未达标 case 持续接近 1，且当前修改方向有效，仍可保留方案继续局部优化。

如果只有一两个 case 不达标，可能与融合方案有关，也可能只是特定 shape 的分块、尾块或固定开销问题。先考虑局部优化；只有证据表明现有方案存在结构性限制、局部修改难以解决时，再考虑换方案。必要时可以让不同 shape 使用不同实现。

## stage3 的方案选择记录

stage3 写代码前读取 JSON 融合算子库，看到各候选方案的 Jev 概率，并结合 stage9 的意见和已有实测结果选择实现方式。

stage3 分别产出以下内容：

| 产出 | 内容 |
|---|---|
| 本轮 JSON 融合算子库 | 更新实际选择的方案、尝试记录及新发现的方案。保留已有 Jev 概率；新增方案没有评分时标记未评分，不自行编造概率。 |
| 《融合方案选择决策依据.md》 | 写代码时单独说明：选了哪个方案、参考了哪些概率和证据、针对哪些 case、实际改了什么、为什么预计有效；若保留原方案或未选最高概率方案，说明理由。 |
| 自测报告 | 记录给定 case 的实际运行结果；另做“同 shape、更换输入数据、权重或偏置、连续调用”的验证，逐次对照参考结果，确认使用当前参数。已有 case 通过不能替代此项；未执行或失败须明确记录。与方案选择依据分开。 |

stage7、stage8、stage9 都增加输入《融合方案选择决策依据.md》，读取与当前被评测代码对应的版本：stage7 对照选择理由分析瓶颈及未达标 case 的变化，stage8 据此搜索改进方向，stage9 综合历史趋势判断下一轮是否换方案。

stage9 的新意见交给 stage3 执行后，stage3 再输出下一版选择依据，供后续评测和审查使用。首轮尚无 stage3 产物时沿用现有设计材料，不改变首版流程。

## 需要调整的审查原则

1. stage3 找到更好的融合方案，且真实评测证明有效，不应因为偏离原计划或不在初始方案库中，就强制改回。
2. P0/P1/P2 保留，只取消“融合方向永远最高优先”的固定要求。优先解决正确性和未达标 case，再提升整体性能。
3. stage9 按实际数据判断方案是否值得保留，不以单 kernel、多 kernel 或中间结果是否经过 HBM 单独判定优劣。
4. 取消旧的“性能达标后必须证明单 kernel 真融合才能退出”条件；stage9 的旧退出判断不能绕过新的 x 次窗口。
5. Jev 概率作为选择参考，不能压过真实评测；stage9 应检查 stage3 的选择理由是否成立，而不是只检查它是否选择了最高概率方案。

## 统一口径

最佳实现比较和 x/y 窗口须使用同一硬件、同一 case 集合及一致的 baseline、计时策略；口径不一致或计时有疑问的历史成绩不参与比较和窗口计算，按当前口径重新评测后再纳入。

累计提升使用窗口开始时与结束时的最佳 avg_speedup 比较，不累加逐轮百分比，也不把退步后的恢复误算成新提升。未达标 case 的趋势用于 stage9 判断优化方向，不替代 avg_speedup 的 5% 窗口指标。编译失败、精度失败和无效性能评测不计入 x/y，仍按原流程处理。

单轮涨跌的 knowledge 规则不变：与最近一轮 avg_speedup >0 的结果比较，变化百分比保留一位小数后判断 ±5%。恢复代码不算新评测。两类停滞触发、退步处置均输出 `=====` 日志；停滞按场景累计进入次数，恢复同轮不重复计数。次数存于 `selection/semantic_events.json`，退步处置及恢复前代码存于 `selection/rollbacks/iterN/`。

上述规则已吸收 v1/v2 的案例结论：平均变化很小时慢 case 仍可能明显改善、按 shape 缓存可能复用旧数据、旧计时成绩不可直接比较。具体数据和静态阅读依据见完整版；本轮未重新评测，不据此判断两版真实快慢。

已落实：n 默认 3；x/y 默认均为 3，在 `workflow.semantic_exit` 配置。窗口需要一份基线加 x/y 次有效成绩，达标状态变化时重置。`selection/best.json` 保存最佳清单，`selection/records/iterN-指纹/` 保存对应代码、方案及报告副本；首次有效性能评测前不建立最佳记录。Stage10 使用最佳已评测快照，详见 README 的“最佳融合实现”说明。仅完成离线验证，未重新运行 NPU 评测。
