# 人类在环与 Stage9 场景裁剪：改动计划与实现状态

依据[已确认的人类参与方案](<workflow_human_review_design.md>)和[按场景的 Stage9 review](<workflow_stage9_review.md>)。前三步已接入代码，保留下列设计与验收要求便于 review；第四步中的真实模型、NPU 联调尚未完成，不能把离线模拟当作实际调优效果。

**范围：** 接入主动介入、第三次停滞咨询；同时裁剪 Stage9 的场景任务和输入。继续使用一个 Stage9，不拆多个决策节点。

**保持：** 原有编译/精度/性能路由、最佳实现排序与快照、x/y 和 5% 窗口、单轮 ±5% 知识记录、最大迭代次数。已达标分支仍不经过 Stage7/8；刚修复的独立 decision 和程序合并账本继续沿用。

## 第一步：按场景组织 Stage9（已接入）

把原 role 收为共用规则，再按程序判定的场景加载任务；不再“完整 role 全部注入，再告诉它忽略一部分”。默认输入同样裁剪，原始材料留存并提供路径、用途和读法。

- **编译失败：** 编译日志、自测、代码和相关历史；只做故障归因、修复方向与必要争议裁定。
- **精度失败：** 精度差异、case/golden、自测及连续调用；只做正确性修复判断。
- **零分/报告异常：** 按实际错误核对报告、代码及规则，不要求正常性能优化；缺报告不能当作已证实作弊。
- **普通未达标优化：** Stage7/8 结论、当前方案、慢 case 趋势、相关历史；做方向取舍和知识记录。
- **停滞审查：** 普通优化材料加窗口和候选方案重点比较；保留“慢 case 仍改善时可以继续”的判断。
- **达标继续优化/收尾：** 使用实际性能与必要原始证据，不要求不存在的本轮 Stage7/8 结论；是否退出由程序给定。

人工处理作为原场景上的附加任务，区分“正常决策、生成咨询问题、收到反馈后复议”。保存原场景和失败原因，恢复后继续同一任务。这是人工等待的必要衔接，只补 Stage9 的恢复，不重写整个状态机。

**验收：** 每个场景只出现对应任务；没有正式性能成绩时不要求性能经验；原有失败回退、知识记录和语义退出仍通过测试。

## 第二步：接入主动意见（已接入）

入口为 `tools/human_review.py --work-dir <work> --text "意见"`。在另一终端向指定工作目录提交，避免和正在运行的 agent 抢输入；纯提问加 `--kind question`，状态查询用 `--status`。程序保存意见编号、原话、接收时间及处理状态。

**流程：人提交 → 程序保存 → Stage9 按原场景处理 → 人工 P0 → Stage3。**

- 不打断当前节点；在 Stage9 下发建议、Stage3 启动和正式退出前检查新意见。已有决策但尚未交付时，先复议。
- Stage9 逐条关联人工意见与 P0；纯提问先答疑，等待表达不当作方向。正确性或硬件冲突必须解释并给替代方案。
- Stage3 在《融合方案选择决策依据.md》和 `develop/<iter>/human_feedback.json` 中记录落实情况；程序保留“已处理”和“已执行”的区别，落实回执不等于性能已验证。
- 退出条件或迭代上限导致无法执行时，交 Stage10 说明原因，不突破原限制。结束后的任务不因迟到意见自动重开。

**验收：** 任意节点运行时都能提交；意见不丢失、不重复消费，Stage3 实际收到人工 P0，退出前不存在静默遗漏。

## 第三步：接入第三次停滞咨询（已接入）

程序按新增有效评测轮次累计触发次数；满 y 且窗口累计提升 <5% 才算，重跑/恢复不重复，允许窗口重叠。第 3 次必须求助；咨询完成、全部达标或窗口提升恢复到 ≥5% 后清零。

**流程：Stage9 写问题 → 程序等待 → Stage9 复议 → 提交最终决策 → Stage3。**

- **第一次调用只咨询：** 生成难点、尝试、证据、2～3 个选项和推荐方案，先输出 `question.json`，程序校验后生成《问题文档.md》。不要求此时填完整 ledger/P0，也不立即合并账本或下发修改。
- **程序等 2 分钟：** 问题通知后开始计时；正式意见立即结束等待。“请等待／等待一会儿”只延期一次，在原截止时间上加 10 分钟，最长 12 分钟。
- **回复后复议：** 完整打包原问题、所有选项与推荐理由、人的全部回复、原场景及证据版本。Stage9 优先处理新意见，必要时回查原始材料，形成最终 decision。
- **超时：** Stage9 按推荐方案形成最终决策，明确未收到人工意见，不能写成人工同意或人工 P0。迟到回复转主动介入。
- **统一提交：** 最终 decision 仍须补齐本轮应有的成功/退步经验与裁定。咨询、等待、复议都不增加评测轮数或 x/y；同一评测的经验更新原条目，不重复追加。

**验收：** 第 3 次才问；普通回复提前结束、等待指令最多延期一次、超时继续、迟到转交均正确；恢复沿用原截止时间，不再发同一个问题或重复计数。

## 第四步：离线回归与实际任务验证

已增加场景裁剪、人工协议、时间窗口与路由的离线测试，回归同时覆盖原有语义退出与知识记录。后续仍需真实模型与 NPU workflow 验证，尤其是问题选项是否有用、人工意见落实质量及优化收益。

`config.yaml` 的 `workflow.human_review.proactive_enabled`、`consultation_enabled` 分别控制主动入口和自动咨询，默认开启。2 分钟、一次额外 10 分钟及第 3 次触发按确认方案固定执行。

重点检查：人类意见刚好在 Stage9 完成时到达；咨询后中断恢复；人工要求与硬件冲突；全部达标即将退出时仍有意见；人工复议不重复写 ±5% 经验，也不改变最佳成绩。

## 已修改的位置与留存文件

- **`lib/stage9_scenes.py` 与 `roles/stage9/`：** 共用规则、六类场景及人工处理阶段；编译/精度失败不再背负整套性能分析任务。
- **orchestrator 与状态保存：** 接收意见、计数、等待、原场景恢复、交付前检查；按咨询/最终决策分别验收。
- **`lib/human_review.py`、`lib/stage9_human.py` 与 `tools/human_review.py`：** 接收原话、持久保存消息、版本证据和截止时间；模型不负责计时或改变计数。
- **Stage9 输出校验、Stage3/10 提示：** 增加意见编号与处理结果，检查人工 P0 是否传递；记录落实或无法执行原因。保持程序合并旧账本的保护。
- **`<work>/human_review/`：** 保存待处理意见、状态；每次咨询在 `<iter>/<请求编号>/` 留存问题、完整对话、证据清单和反馈包。既有材料引用明确版本或快照，变化时留副本，缺失须注明。
- **`<work>/knowledge/stage9/`：** 沿用每次独立请求和 decision 留档，增加实际 `prompt.md` 与场景 role，关联对应人工记录；最终由程序写 history 和知识 Markdown。
