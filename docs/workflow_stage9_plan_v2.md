# Stage9 结构化修改方案

**Stage9 要说清楚：改哪个 case、改哪个文件、具体怎么改、哪些文件不能动。程序检查填写的字段和文件范围，通过后再交给 Stage3；这不代表技术分析一定正确。**

文档里的“版本 2”只是新 JSON 格式的编号，没有新增 Stage。

## 1. Stage9 要写什么

假设 case7 使用 `c2.py`，这一轮不能修改 `c3.py`。Stage9 要填写：

- **要解决什么：** case7 的精度问题，优先级 P0。
- **对应哪个文件：** `impl/c2.py`；同时说明从哪里看出 case7 使用它，例如 dispatcher 中的哪个分支。
- **具体怎么改：** 修改 c2 的尾块处理，让最后不足一整块的数据也能正确计算。
- **哪些文件不能动：** `impl/c3.py`，以及本轮需要保护的其他文件。
- **改完怎么检查：** 重新运行给定用例，确认精度通过并留下测试日志。

如果只需要查看原因，就写“检查”，不能在后面又要求修改。编译配置等不针对某个 case 的问题，可以写“整个算子的工程问题”，并说明原因。

## 2. 为什么不用再填一遍“允许修改的文件”

还是上面的例子：Stage9 在步骤中填写 `file = impl/c2.py`、`operation = modify`，程序就把 `impl/c2.py` 记为本轮允许修改的文件。**程序读取这两个明确字段，不是从“修改 c2”这句话里猜文件名。** Stage9 不用再重复填写一张“允许修改的文件清单”。

程序会遍历所有建议的所有步骤：`modify`（修改）和 `create`（新建）计入允许清单，`inspect`（检查）不计入；同一个文件出现多次，只汇总一份。10 个、100 个文件都按这个规则处理，没有固定数量上限，也没有写死 c2、c3 这些名称。

文件多时，Stage9 仍须逐个列出实际要改的文件，不能用“整个目录”或 `*.py` 代替。**如果它漏写了一个必须修改的文件，程序不会自动补出这个文件。** Stage3 应报告缺项，不能自行扩大范围。

**“不能修改的文件”则由 Stage9 集中写在一个地方，所有建议都要遵守。** 例如写了“c3 不能动”，无论这一轮有几条建议，都不能再要求修改 c3。

所以，Stage9 要填写的是：

- 在每条建议里写清楚：**修改哪个文件、怎么改。**
- 在本轮的禁止清单里写清楚：**哪些文件不能改。**

程序把这些明确字段对照检查，拦住能直接查出的冲突。

## 3. 程序会拦住哪些问题

- **前后说的不一致：** 填写“case7 对应 c2”，修改步骤却只写“修改 c3”。
- **要求修改禁止文件：** 步骤要求改 c2，禁止清单里也有 c2。即使出现在不同建议中，也不允许。
- **操作字段矛盾：** 建议类型填“只检查”，文件操作却填“修改”。如果只是方法文字里暗含修改，程序目前不能可靠识别。
- **没有交代清楚：** 缺少目标文件、具体改法、case 对应代码的依据或验收要求。
- **文件或编号不对：** 要修改的文件不存在；或者目标 case 不在程序拿到的完整用例清单中。新建文件要明确写“新建”。
- **路径实际冲突：** 两个名字实际是同一文件，却一边允许改、一边禁止改；或者把一个文件同时当作另一个文件的目录。
- **要求修改固定输入：** 原始需求、参考答案、评测报告、history、最佳快照及程序状态等有固定保护，不能靠漏填禁止清单获得修改权限。

多个硬链接共用同一份文件内容时，修改其中一个会影响其他名字指向的内容。程序允许读取，但拒绝直接授权修改，需先准备独立副本；程序不自动解除链接。

检查不通过，就把能独立检查的错误一起交回 Stage9，包括多条任务冲突、多个文件路径错误和字段缺项。最多修正两次：首次生成加两次修正，共尝试三次；第三次仍不通过就停在 Stage9，不把错误建议发给 Stage3，也不增加性能迭代次数。JSON 无法解析或某段结构错误时，先修复这些错误，再检查依赖它们的内容。

**程序仍可能漏掉什么？** 如果 Stage9 一开始就把“case7 对应哪个文件”填错，程序未必能发现。这里要求 Stage9 写出查代码的依据，Stage3 再核对实际代码，不能把“JSON 检查通过”当成“分析一定正确”。

评测报告不完整时，程序也不会把报告里已有的几个 case 当成全部用例；缺少的部分仍要查原始输入。

**还有一个尚未实现的检查：Stage3 实际改了哪些文件。** 目前程序在交接前检查方案，执行时靠提示词约束；Stage3 返回后尚未把实际文件变化逐一对照允许清单。专项离线测试已复现：模拟 Stage3 修改禁止文件，现有流程仍继续。这是测试中构造的情况，不代表历史任务已发生同样的问题。

下一步建议补执行后检查：比较源文件的新增、修改和删除，越界则记录差异并阻止交付。实施前需区分源码与自测生成的缓存、日志，并保留断点恢复时的原始对照版本；本轮未加入这一流程。

本次验证：200 条建议、2,001 个不同文件的汇总与恢复检查通过，另验证了 600 个新文件共用目录等情况。全量 474 项离线测试通过；未运行真实大模型或 NPU。

## 4. Stage3 怎么看，结果存在哪里

Stage3 看到的是按编号整理的建议，每条都有：**优先级、目标 case、对应文件及依据、具体改法、验收要求**，同时看到本轮不能改的文件。

每轮方案都会保存：

- `knowledge/stage9/<iter>/<请求编号>/decision.json`：Stage9 这次填写的原始方案。
- `knowledge/history.json`：各轮记录；`ledger[].action_plan` 保存该轮方案，`suggest_next` 保存最新建议。
- 如果需要修正，错误保存在该次目录的 `validation_error.json`，`errors` 列出完整错误清单。两次修正分别放在原请求下并列的 `retry1/`、`retry2/`；每次有独立请求编号、提示词和决策文件，日志记录当前是第几次尝试。

从 Stage3 断点恢复时也会检查。旧格式的历史继续保留；要继续执行旧建议，先让 Stage9 按新格式补全。如果本轮需要回退最佳代码，就按回退后实际要修改的代码检查方案。

原有性能判断、提升或退步达到 5% 时的经验记录、最佳版本选择和人工 P0 规则保持不变。

以上路径都从本次工作目录 `<work>` 开始；`<iter>` 是 `iter1`、`iter2` 等轮次目录。

这些文件放在本次 Stage9 请求目录中：

- `decision_schema.json`：规定 JSON 应有哪些字段、各字段填什么类型。
- `decision_template.json`：给 Stage9 填写的空白模板。

修正时，`retry1/`、`retry2/` 中也会保存对应文件；每次修正都保留原场景和人工意见，并引用上次被拒绝的决策与错误。JSON 中的 `plan_version: 2` 供程序识别格式，用来处理旧历史的兼容问题。
