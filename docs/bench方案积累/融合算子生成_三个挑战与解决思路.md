# 融合算子生成：三个挑战与解决思路

融合不只是把代码合起来。它要同时解决三个问题：**怎样合才更快、合完是否算对、测完之后该怎么改。**

## 1. 单个算子都很快，合起来未必快

**难在哪里：** 不同计算适合的分块和并行方式往往不同。融合要求它们共享中间数据，可能省了搬运，却增加存储占用和等待，反而变慢。昇腾上还要协调 Cube 与 Vector。因此，融合哪些步骤、数据怎么切、内存怎么用，必须一起考虑。

**论文中的例子：** Welder 调整矩阵乘与 Softmax 的分块后，两者单独运行都变慢，融合后的整体却更快。这说明，单算子的最优方案不能直接拼成融合的最优方案。[依据](融合算子挑战_论文资料/03_融合与资源权衡/阅读笔记.md)

**现有方法的局限：** 编译器已经能搜索融合方案，但受支持的计算和调度方式限制；Agent 更灵活，但只在当前方案上反复改代码，可能一直调不对方向。

**我们怎么做：** 结合硬件保留全融合、部分融合、拆分等候选，写清选择理由，再用实测决定保留还是更换。Jev 负责初始排序，实测结果决定后续判断。

## 2. 单个算子都算对，融合后仍可能出错

**难在哪里：** 融合改变了中间结果的计算顺序、存放位置和使用时机。例如，Softmax 需要整行统计量，不能把各块分别归一化后直接拼接。舍入、同步或旧数据复用的问题，还可能只在特殊输入或连续调用时出现。

**论文给出的提醒：** EAGLE 发现，预期等价的优化实现也会悄悄算错；OATest 发现，融合后的子图与外围代码组合，还会触发新的编译问题。[EAGLE](融合算子挑战_论文资料/01_等价性与测试/论文阅读笔记.md)、[OATest](融合算子挑战_论文资料/02_编译与优化测试/论文阅读笔记.md)

**现有方法的局限：** 单算子测试或少量固定输入，难以覆盖融合新增的相互影响。已有专门测试研究，但接上普通测试流程，不等于具备了这些能力。

**我们怎么做：** 检查完整计算链的结果，要求同 shape 更换输入等数据连续测试；将报告与代码版本绑定，代码改了就不能继续使用旧测试结论。目前是测试与证据管理，尚未实现自动等价图测试或完整正确性证明。

## 3. 测出哪里慢，不等于知道该怎么改

**难在哪里：** 同一融合方案可能适合小输入，却拖慢大输入；慢的原因可能是融合方式不对，也可能只是分块不合适。平均成绩又会掩盖差异：多数 case 变快时，少数可能变慢；平均不涨时，最慢 case 也可能正在改善。

**现有方法的局限：** KernelGen、Kernel-Smith 已有性能反馈和历史记录。仍需研究的是：怎样利用这些信息，判断应当继续局部调优，还是更换融合方案。[对比依据](三项工作与当前融合算子生成方法对比.md)

**我们怎么做：** 一起看每个 case 的瓶颈、历轮变化和对应代码。少数慢 case 在改善，就允许保留方向；未全部达标且提升停滞，再重点审查替代方案。重大分歧引入人工意见。最终优先交付精度通过、全部 case 不慢于基准的版本，再比较平均加速比，并保存实现和报告。

## 当前方案的重点

**先选融合方向，再验证是否正确，最后根据各 case 的实测持续修正方向。** 第一、三点更体现本项目特色；第二点是必要保障，目前不能单独称为新的验证方法。

已有方法能生成融合算子，我们的效果仍需对比实验验证。另外，当前评分主要统计 kernel 执行时间，不能直接据此声称整个调用过程更快。
