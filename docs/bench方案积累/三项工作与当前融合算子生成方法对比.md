# 三项工作与当前融合算子生成方法对比

核对日期：2026-09-25。只比较融合算子生成方法：**哪些计算合并、在哪里拆分、如何安排数据，以及怎样根据实测调整方案。** 编程语言不作为方法差异；以后切换 DSL，下面的比较仍然适用。

材料范围：KernelGen 依据公开流程和 Skills，其综述与 KernelGenBench 不能当作平台算法实现；Kernel-Smith 依据论文及公开的算子贡献；超大 Kernel 材料是研究计划。**公开了算子、工具或评测代码，不等于公开了完整生成系统；缺少完整源码，也不等于方法没有融合能力。** 下面比较方法设计，不能代替统一硬件上的实测排名。

本次扩大检索补充三点：

- **KernelGenBench 有真实 Agent 运行与验证代码。** `agent_bench/` 包含调用、反馈工具和 Ascend 适配，提示词也要求融合优化；不能把它说成只有评测器。但它是基准中的被测方法与运行流程，不是 KernelGen 平台内部生成服务。[代码入口](KernelGen/github/KernelGenBench-main/agent_bench/run.py)、[闭环及融合要求](KernelGen/github/KernelGenBench-main/agent_bench/methods/normal_cc/templates/instructions.md)
- **Kernel-Smith 开放了部分数据与生成成果。** 论文作者关联账号发布 Seed、SFT、RL 数据，且有公开算子贡献；尚不能据此复现完整 Agent 与模型。公开 SFT 数据也不能直接等同于论文报告的完整训练数据。[数据集合](https://huggingface.co/collections/CoopReason/kernel-smith)、[项目说明及算子链接](https://github.com/InternLM/Kernel-Smith)
- **超大 Kernel 原方案的公开来源未确认。** 文中提到的 TVM、MLIR、ExecuTorch 是已有开源基础设施，不是该方案自己的实现；其他近名项目也不能替代其源码。[来源核查](超大Kernel生成与测试迭代演化闭环/超大Kernel技术方案_分析.md)

## 1. 放在一起看，各自怎样做融合生成

| 方法 | 融合方案怎样形成 | 下一轮怎样探索 | 经验怎样利用 |
|---|---|---|---|
| **当前方法** | 给定融合需求，Jev 筛选方法候选；开发节点记录实际选择及理由，可拆分、部分融合或按 shape 选不同实现。 | 主要沿一条实现路线迭代；Stage9 根据方案依据、瓶颈、逐 case 趋势及历史决定继续、局部修改或换方案。 | 保留实现与评测证据，记录成功和退步原因；人工方向作为 P0 进入下一轮。 |
| **KernelGen** | 从需求检索参考实现，再生成和优化代码；支持融合任务，完整的内部方案搜索机制未公开。 | 公开 Skill 将当前代码、各 shape 成绩、分段耗时和历史提交给优化服务，维护正确版本及最佳版本。 | 当前任务历史进入优化上下文；网页支持人工修改、重测和选版本。 |
| **Kernel-Smith** | 对给定模块生成代码候选；公开产物包含专用／通用分支、部分融合及多 kernel 实现。 | 从高性能及不同特点的候选中选择参考，产生新版本并实测，持续维护候选库。 | 用执行反馈指导搜索；另将有效修改步骤用于离线微调和强化学习。 |
| **超大 Kernel 方案** | 计划从模型中选择融合区域，将融合边界、分块、布局、并行和精度作为可调整参数。 | 计划在资源约束下搜索参数，根据访存、寄存器溢出等现象缩块、拆分或重排。 | 计划保存参数、成绩和失败标签，复用相似任务的优化经验。 |

## 2. 当前方法最值得强调的区别

FlagOS 的另一个本地 TLE 开发 Skill 也公开了性能记录、保留／回退和成功／失败经验模板。它不等于 KernelGen 平台后端，但进一步说明“记录经验、按结果保留或回退修改”不能单独作为我们的独有贡献。[具体模板](KernelGen/github/skills-main/skills/tle-developer-flagos/references/workflow-templates.md)

**第一，把融合方案的选择和修改依据明确留下来。** 我们要求说明选了什么、针对哪些 case、为什么预计有效，再将选择依据与被评测代码绑定，供后续节点核对。相较 KernelGen 已公开的通用优化流程，我们更明确地组织了“提出融合方案 → 实测验证 → 审查是否继续”的决策过程。Jev 概率只是初始参考，不能当作性能收益，更不能压过实测。

**第二，把少数慢 case 和整体停滞分开处理。** 全部 case 不慢于基准后，x 次有效迭代的最佳平均加速比累计提升不足 5%，才按语义条件交付最佳版本；仍有慢 case 时，y 次停滞触发方案审查。少数 case 持续改善时，可以保留方向，也允许按 shape 使用不同实现。KernelGen 公开 Skill 按目标加速比或轮数结束；Kernel-Smith 的 40 轮是实验预算；超大 Kernel 的综合评分与收敛条件尚未细化。**这体现我们交付规则更具体，不能直接推导出搜索效果更好。**[当前判断规则](../workflow_performance_decision_rules.md)

**第三，将专家方向意见接入可追溯的执行过程。** 人工意见经 Stage9 形成 P0，由开发节点说明如何落实；未达标停滞多次触发后，还会提出选项并主动咨询。其他工作也有人工操作或专家参与，我们的特点是将“意见如何改变下一轮”写成了明确流程。[人工参与方案](../workflow_human_review_design.md)

## 3. 对比后，我们还缺什么

**相对 Kernel-Smith：实际代码探索还不够多样。** Top N 融合方法不是 N 个已经实测的代码分支，保存历史最佳也不等于持续维护多条探索路线。单线修改仍可能受早期选择限制；另一方面，它的代码候选搜索也不能直接等同于显式的融合方法搜索。

**相对超大 Kernel 方案：融合参数还未形成统一搜索表示。** 我们已有拆分融合、按 shape 路由和资源核算要求；但融合边界、分块、布局、缓冲等信息主要由 Agent 在文档和代码中表达，尚未形成统一的参数搜索与资源检查模块。对方提出了这种结构化方向，效果仍待验证。[现有方法库](../../knowledge/fusion_options.json)、[资源核算要求](../../roles/n1_stage2_first_impl.md)

**相对这些工作：方法效果还需要统一实验说明。** 有闭环、profiling、知识记录，并不足以证明融合生成更有效。尤其需要证明：Jev 是否减少试错，Stage9 是否选对修改方向，语义退出是否节省成本而没有漏掉明显收益。KernelGenBench 可借鉴的是覆盖测试和成本统计，不能用其中其他 Agent 的成绩证明 KernelGen 平台更强。[评测论文](KernelGen/papers/02_KernelGenBench_2607.27231v3.pdf)

## 4. 建议优先补的三件事

1. **把方法候选变成少量实测代码候选。** 对有分歧的融合任务，保留全融合、部分融合或按 shape 路由等不同实现，让 Stage9 比较实际收益；不要求每轮都运行全部方案。
2. **把“改了什么、为什么有效”记录得更具体。** 关联融合边界、分块、布局、数据搬运、资源占用和受影响 case，便于复用有适用条件的经验。
3. **在相同任务、模型和时间预算下拆开验证。** 分别检查融合评分、历史经验、人工指导的增益；比较全部 case 达标率、最慢 case、平均加速比、评测次数和总成本。退出规则另看节省多少预算、是否错过后续收益。

**当前方法可以定位为：围绕融合方案选择、逐 case 验证、跨轮审查和专家指导组织开发的 workflow。** 后续最有价值的增强，是在这套流程上补充实测候选探索和结构化融合参数，并用实验验证收益。
