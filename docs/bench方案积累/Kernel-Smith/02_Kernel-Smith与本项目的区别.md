# Kernel-Smith 与本项目的区别

更新日期：2026-09-25。依据论文 v2、官方仓库、作者关联数据集、三个上游 PR 和本项目代码；未复现实验，不作跨平台性能排名。

## 共同点

两者都用“生成 → 编译与精度验证 → 性能评测 → 反馈修改”持续优化算子，也都涉及融合算子。Kernel-Smith 同样保存代码、成绩和失败信息，供后续选择与修改。因此，“有闭环、有历史、有实测反馈”本身不是我们的独有特点。[论文 §3](papers/00_Kernel-Smith_2603.28342v2.pdf)

## 主要区别

**1. 都面向给定计算模块的融合开发。** 两者都在功能和测试约束下寻找更快的实现；区别应看怎样搜索候选、修正方向和利用经验。现有结果的任务与评测平台不同，因此性能不能直接横比；实现语言本身不构成方法差异。[论文 §3、§5.3](papers/00_Kernel-Smith_2603.28342v2.pdf)、[本项目 README](../../../README.md)

**2. 它搜索多个代码候选，我们主要沿一条迭代线推进。** 它从候选库中挑选高性能及不同特点的实际代码，继续生成新版本，减少一直困在同一路线的风险。我们由 Stage1.5 的 Jev 筛选融合方法，再由 Stage9 指导修改，保留历史和最佳实现。**Jev 的 Top N 是方法候选，不等于多个经过实测、共同参与搜索的代码候选。**[论文 §3.2](papers/00_Kernel-Smith_2603.28342v2.pdf)、[融合选择代码](../../../lib/fusion_selection.py)

**3. 它把优化经验用于训练模型，我们主要用于指导后续节点。** 它离线筛选有效修改步骤，进行微调和强化学习；运行时搜索与模型训练是两层流程，不是每改一次代码就训练一次。我们将成功经验、退步教训写入 knowledge，结合历史再提供给 Agent，目前没有对应的模型训练流程。[论文 §4](papers/00_Kernel-Smith_2603.28342v2.pdf)、[我们的经验记录规则](../../workflow_performance_decision_rules.md)

**4. 我们明确规定了交付条件和人工介入方式。** 我们按逐 case 达标情况、x/y 次有效迭代的提升判断退出或审查，保存代码、融合方案、HAP、平均加速比和评测证据；人工方向意见经 Stage9 作为 P0 转交 Stage3。论文重点是搜索和训练，未公开同款退出与人工协议；其 40 轮是基准实验预算，不能当作通用退出规则，也不能据此说它没有人工参与。[论文 §5—6](papers/00_Kernel-Smith_2603.28342v2.pdf)、[我们的判断规则](../../workflow_performance_decision_rules.md)、[人机方案](../../workflow_human_review_design.md)

**5. 有公开内核和数据，完整生成系统尚不能审查。** 官方主仓库仍只有 README、LICENSE，明确暂不公开模型权重和 agent 代码；另有三个已合入的融合实现和作者关联的三份训练相关数据。代码已体现部分融合、多内核及条件分支，不能将这些能力说成我们独有。完整系统缺少复现条件，不代表其性能差，也不代表我们已优于它；其基准指标不能直接等同于我们的 avg_speedup。[公开材料及检索范围](Kernel-Smith_论文主线分析.md#5-公开材料能确认什么不能确认什么)、[实验口径](Kernel-Smith_简要分析.md)

## 对我们的启发

优先借鉴两件事：保留少量方法不同、经过实测的代码候选，让 Stage9 有具体版本可比较；把修改前后的代码、输入、成绩和原因关联起来，为复盘及未来训练积累材料。

**先验证多候选是否减少无效迭代、改善慢 case，再考虑模型训练。** 训练还需要数据清洗、执行筛选和算力投入，不能把已有 knowledge 文档直接当成训练数据。
