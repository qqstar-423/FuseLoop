# 超大 Kernel 技术方案：简要分析

依据原文和本项目现有代码整理。原文是四年研究计划，预期指标不能当作已实现的效果。

## 1. 他在干什么

想做一套**面向多种端侧芯片的模型编译与自动调优平台**。

输入整个模型，找出适合合并的一段计算，在硬件资源允许时生成一个或少数几个大 Kernel；编译、实测后，根据结果继续调整融合范围、数据分块、内存布局、并行方式和精度，最后输出可部署代码。

为此，他计划建设分层中间表示（IR）、多芯片编译后端、评测系统和优化引擎，并把每次参数、成绩和失败原因存下来，供下一轮及其他芯片复用。

## 2. 针对什么问题

- **运行开销大：** 小 Kernel 启动频繁，中间数据反复搬出片上内存。
- **融合容易过头：** 端侧存储和寄存器有限，融合过大会溢出，反而变慢。
- **调优、迁移成本高：** 分块和调度依赖专家经验，换芯片后难以直接复用。

## 3. 方案怎么样

**方向合理，资源约束考虑得比较完整，但目前只能评价设计，不能确认效果。**

优点是明确“融合不是越大越好”，同时考虑延迟、存储、能耗和精度；把失败现象对应到修改办法，比只记录一个性能分数更有用。

主要缺口是：综合评分怎么算、变换如何保证正确、贝叶斯优化／强化学习／大模型如何分工、何时算收敛，都还不够具体。多套 IR、多类芯片和多种搜索算法一起建设，落地工作量很大。性能提升 10%—50%、访存降低 20%—80% 是目标，文中没有对应实测结果。

## 4. 和我们项目有什么区别

- **范围不同：** 他从完整模型出发，规划模型区域并建设编译基础设施；我们从给定计算需求和 case 出发，组织昇腾 PyPTO Pro 融合算子的开发迭代，也能处理较大的融合任务。
- **优化方式不同：** 他计划搜索“融合、分块、布局、并行、精度”参数，并组合多种算法；我们由 Jev 提供初始候选，cannbot 写代码，cannbench 评测，Stage7/8/9 分析和指导，再接收人工意见。
- **判定与落地不同：** 他计划综合评价延迟、资源和能耗；我们以精度通过、所有 case 不慢于基准、平均加速比及停滞窗口做明确判断，并已有最佳快照、经验记录、断点恢复和人工参与的控制代码。代码存在不等于硬件效果已全面验证。

对我们最有用的是：**把每轮分块、布局等参数和失败标签记录得更结构化，逐步补充资源指标。** 这些可以增强现有 workflow，无需先重建他的整套编译平台。
