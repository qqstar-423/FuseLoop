# 超大 Kernel 方案与本项目的区别

方案对比日期：2026-09-24；来源复核日期：2026-09-25。对照[原方案](面向端侧异构芯片的超大Kernel生成与测试迭代演化闭环技术方案.md)与本项目代码。所给材料是四年研究计划，未提供实现源码和实测结果；扩大检索后仍未确认其作者、对应公开项目或 910 复现入口，不能据此断言外界没有实现。详见[来源与开源复核](超大Kernel技术方案_分析.md#5-来源与开源复核2026-09-25)。以下区分设计目标与已有实现，不作性能排名。

## 共同点

两者都希望用“生成 → 实测 → 分析 → 修改”持续优化融合算子，并留下历史成绩和失败经验。原方案也明确“融合不是越大越好”，允许生成一个或少数几个 Kernel。因此，“做融合、有反馈、有知识库”本身不是我们的独有特点。[已有简要分析](超大Kernel技术方案_分析.md)

## 主要区别

**1. 输入与优化范围不同。** 原方案从完整模型出发，自动选择适合融合的模型区域，面向 NPU、GPU、MCU 等端侧芯片。我们从给定计算需求和 case 出发，聚焦昇腾 PyPTO Pro 融合算子的开发迭代。我们也能处理较大的融合任务，但当前没有从完整模型自动划分待优化区域的流程。[本项目 README](../../../README.md)

**2. 建设的工具层次不同。** 原方案计划建设分层中间表示（IR）、融合搜索、内存规划和多芯片代码生成后端，是一套编译与调优平台。我们复用 PyPTO Pro、CANN 和 cannbench，组织 cannbot 写代码、评测、分析及方向调整，重点在开发流程控制；当前不自行建设上述编译器体系。[主程序](../../../orchestrator.py)

**3. 选择下一步的方法不同。** 原方案把融合、分块、布局、并行和精度统一编码成可搜索参数，计划结合贝叶斯优化、强化学习和大模型更新候选。我们由 Stage1.5 用 Jev 评估融合方法，筛选 Top N；后续由 Stage7/8/9 结合实测和历史判断，再交 Stage3 修改。前者提出参数搜索机制，后者已有融合候选与 Agent 迭代流程，不能将 Jev 概率当成实测收益。[融合选择代码](../../../lib/fusion_selection.py)

**4. “最好”和“何时结束”的标准不同。** 原方案计划综合考虑精度、延迟、存储和能耗，但评分权重及收敛条件尚未细化。我们在精度通过、证据有效的版本中，优先选全部 case 不慢于基准的版本，再按平均加速比排序；全部达标后 x 次有效迭代累计提升不足 5% 则交付，仍有慢 case 时 y 次停滞则重点审查方案。当前并未把能耗等指标纳入最佳排序。[我们的判断规则](../../workflow_performance_decision_rules.md)

**5. 经验记录与人工指导的具体程度不同。** 原方案计划保存参数、成绩、失败标签，并用于跨芯片迁移，未展开人工介入流程。我们已保存代码快照、实现方案、融合方案、HAP、平均加速比及评测路径；Stage9 总结经验，并接收人的方向意见，以 P0 转交 Stage3。停滞咨询、等待和回复重新注入也已有程序处理。[最佳记录](../../../lib/semantic_exit.py)、[人机方案](../../workflow_human_review_design.md)

## 对我们的启发

优先借鉴两件事：一是把每轮分块、布局、并行参数和失败原因记录得更结构化，方便比较哪项修改有效；二是在性能分析中逐步补充片上内存、寄存器压力、数据搬运等证据，让换融合方案有更明确的依据。

**原方案覆盖更广，我们当前把融合算子的迭代控制写得更具体。** 这不等于我们性能更好，也不等于原方案已经完成多芯片适配。应先用实际任务验证现有闭环的收益，再决定是否扩大到模型区域划分和跨芯片搜索。
