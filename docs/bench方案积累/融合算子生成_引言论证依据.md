# 融合算子生成：引言论证依据

2026-09-25。本文整理“现有方法 → 仍有的困难 → 本文切入点”，供后续写引言使用。结合[三项工作综合对比](三项工作与当前融合算子生成方法对比.md)，不展开应用背景，也不把实现语言作为创新点。

## 1. 建议确立的核心论点

**已有 Agent 能生成、验证和优化融合算子。我们要研究的是：如何把融合方案选择、硬件约束、逐 case 实测和跨轮决策明确组织起来，使自动迭代更可靠地实现融合收益。**

“跑不起来”要分清是编译失败、结果错误，还是能运行但没有加速。当前材料不足以支持“现有 Agent 都无法处理融合算子”，也不能据此认定它们在 NPU 上普遍低效。**缺少完整开源实现，只能说明我们无法独立复现，不能作为其融合能力不足的证据。**

## 2. 从人工开发到 Agent，论证怎样衔接

**第一步：人工开发难，难在联合决策。** 开发者需要同时考虑融合边界、分块、布局、数据复用及硬件资源。FusionStitching 说明复用可能增加通信、损害并行度；Welder 说明单个算子的合适分块可能与上下游数据复用冲突。这些证据支持“融合不是合并代码那么简单”，也解释了专家为什么需要反复权衡。[FusionStitching §2.3](https://arxiv.org/html/2009.10924v2#S2.SS3)、[Welder §2—3](https://www.usenix.org/system/files/osdi23-shi.pdf)

**第二步：Triton 降低表达与实现门槛，但没有消除方案设计。** 它通过分块编程和编译优化简化高性能代码开发；开发者仍需组织计算、选择分块和调优候选。其 autotune 在提供的配置集合内试验，并不等于自动求解整个计算图的最优融合划分。不能将 Triton 的出现描述成专门解决 NPU 融合问题。[Triton 原论文，2019](https://research.ibm.com/publications/triton-an-intermediate-language-and-compiler-for-tiled-neural-network-computations)、[官方 autotune 文档](https://triton-lang.org/main/python-api/generated/triton.autotune.html)

**第三步：Agent 将写代码和试验串起来，已经取得实际进展。** KernelBench 明确包含多算子融合任务，并显示执行与 profiling 反馈能够改善生成结果。因此，引言应先承认已有工作的能力，再提出融合决策仍需如何改进。[KernelBench §3.2、§5.1](https://arxiv.org/html/2502.10517v1)

**第四步：把研究问题落在融合特有的决策上。** 有生成、测试和反馈环节，并不自动说明系统能稳定判断：当前慢是融合边界不合适，还是分块、数据搬运或少数 shape 的局部问题。下面将这种判断需求作为我们的研究切入点，效果由后续实验验证。

## 3. 为什么复杂融合需要更有针对性的 Harness

这里的 Harness 指组织需求、工具、评测、历史和决策的运行流程。下表分析通用闭环可能遇到的风险，**不表示所有已有系统都缺少这些能力**。

| 融合生成的特殊性 | 简单迭代为什么可能失效 | 当前方法怎样针对性处理 |
|---|---|---|
| **融合范围与内部执行方式互相影响。** 多融合一步，可能减少搬运，也可能增加资源占用、同步或重算。 | 若把减少 kernel 数量当成目标，可能持续优化一个不合适的融合结构。 | 提供多种融合方法，记录选择依据；允许部分融合、拆分和按 shape 路由，由实测审查方向。 |
| **跨计算单元的数据流必须成立。** 在昇腾上，矩阵、向量和搬运单元协作还涉及布局、存储与执行依赖。 | 数学表达正确，仍可能出现依赖错误、额外搬运或等待；仅修语法不能消除这些问题。 | 注入硬件约束，要求解释数据流，将实现与自测、正式评测及瓶颈分析对应起来。 |
| **融合收益随 shape 和计算比例变化。** 同一方案可能加速多数 case，却拖慢少数 case。 | 只看总体成绩，可能掩盖慢 case；平均停滞也可能掩盖慢 case 正在改善。 | 逐 case 验证并跟踪趋势，区分局部优化与换方案；按达标状态决定继续审查还是交付。 |
| **一次修改可能同时改变多个因素。** 融合边界、分块和布局变化后，收益原因容易混在一起。 | 若缺少与版本对应的选择依据和历史证据，下一轮难以判断哪些经验值得保留，容易重复试错。 | 关联方案、代码、成绩和修改原因；Stage9 综合审查，有分歧时引入专家方向意见。 |

前两项的硬件与融合机制依据见上述融合论文、[AscendKernelGen §3](https://arxiv.org/html/2601.07160v2#S3)和[昇腾官方同步控制说明](https://www.hiascend.com/doc_center/source/zh/canncommercial/80RC3/apiref/ascendcopapi/atlasascendc_api_07_0256.html)。后两项是据此提出的流程风险与设计动机；当前实现对应[融合审查方案](../workflow_fusion_selection_semantic_exit_design.md)、[Stage9 职责](../workflow_stage9_review.md)。

**NPU 表述要限定范围。** 上述具体机制针对昇腾架构；编译器和框架可自动处理部分同步，不应写成所有同步都要人工完成。编程抽象可以隐藏细节，但生成的执行方案仍须满足这些约束。

一个可用的解释例子是 `MatMul → Bias → 激活`：要同时判断矩阵结果怎样交给后续计算、是否增加布局转换或存储压力，以及不同 shape 下融合是否划算。**代码中连着写三个计算，并不能直接证明减少了实际搬运或获得加速。** 此例用于说明决策问题，不是已完成的对比实验。

## 4. 前面三个工作应怎样进入引言

- **KernelGen：** 已支持融合、性能反馈和历史版本。其相关的 KernelGenBench 还开源了 Agent 调用、验证与 Ascend 适配，提示词明确要求迭代修复、调分块和合并 kernel。这些不能冒充 KernelGen 平台后端，但也不能忽略已有开源闭环。我们的区别应落在融合选择依据和跨轮审查如何组织，不能写“对方没有考虑融合”。[平台优化流程](KernelGen/github/skills-main/skills/kernelgen-flagos/kernelgen-optimize.md)、[基准中的闭环与融合要求](KernelGen/github/KernelGenBench-main/agent_bench/methods/normal_cc/templates/instructions.md)
- **Kernel-Smith：** 多代码候选搜索与模型训练是其重点；公开产物已包含部分融合和多 kernel 实现，不能将这种灵活性单独作为我们的创新。作者关联账号还发布了 Seed、SFT、RL 数据，但完整 Agent 与权重仍未公开。我们的切入点是组织方案依据、逐 case 趋势和换方向审查；Top N 方法也不等于其实测代码候选库。[论文及源码核查](Kernel-Smith/Kernel-Smith_论文主线分析.md)、[公开数据集合](https://huggingface.co/collections/CoopReason/kernel-smith)
- **超大 Kernel 方案：** 明确考虑融合边界、资源和参数搜索，与我们的动机有交集。但原文没有可确认的作者、机构或项目链接，扩大检索也未找到能对应到它的公开实现。它可用于内部设计对照，尚不能作为已发表、已验证的方法引用；同名或近名 MegaKernel 项目不能自动算作它的源码。[原方案](超大Kernel生成与测试迭代演化闭环/面向端侧异构芯片的超大Kernel生成与测试迭代演化闭环技术方案.md)

另外，**AscendKernelGen 已直接研究 NPU 生成，它与 FlagOS 的 KernelGen 是不同项目。** 论文链接的官方页面已提供 KernelGen-LM 模型、Ascend-CoT 数据和 NPUKernelBench 代码。因此，“NPU 生成尚无公开研究与实现”也不成立。其特定模型的零样本失败可以说明领域适配的困难，但不能外推到所有 Agent，更不能等同于融合性能失败。[论文表1与实验设置](https://arxiv.org/html/2601.07160v2#S1)、[模型与数据](https://huggingface.co/AscendKernelGen)、[评测及生成入口](https://github.com/weich97/NPUKernelBench)

## 5. 怎样引出我们的方法，哪些结论还要补证据

建议围绕三点组织贡献：**融合方法先验指导探索；实测证据驱动方案审查；跨轮经验与专家意见指导后续修改。** 目标是让每轮修改服务于可验证的融合收益，例如减少实际数据搬运和启动开销，同时避免资源冲突与慢 case 退步。

这里已有的是流程机制，尚不能宣称自动求得最优融合边界、自动完成资源代价建模，或保证优于其他 Agent。Jev 是先验估计；选择依据是待验证的理由；平均加速比提升也不能单独证明收益来自融合。

写成论文结论前，建议补三类证据：

1. **有效性：** 相同模型、任务、工具和预算下，通用闭环与加入融合机制后的成功率、逐 case 性能及成本对比。
2. **原因：** 用访存、kernel 调用或相关 profiling 证据，说明收益来自哪些融合决策；拆开验证方案先验、历史审查和人工指导的作用。
3. **失败案例：** 展示一次过度融合、一次少数 shape 变慢，以及一次停滞后正确保留或更换方向的过程。

引言重点写清“融合为什么需要这样的决策流程”。x/y、5%、P0 和节点编号属于实现细节，留到方法部分。FusionStitching、Welder 可作为融合难点的代表性研究引用，不应未经考证称为“首次提出算子融合”的论文。
