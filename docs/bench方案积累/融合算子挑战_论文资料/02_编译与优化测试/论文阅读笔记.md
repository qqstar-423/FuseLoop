# 编译与优化测试：两篇论文的直接证据

核对日期：2026-09-25。由 [Junjie Chen 主页](https://sites.google.com/site/junjiechen08/)筛选。以下页码均指本目录 PDF 的页序，从 1 开始；两份 PDF 均为 13 页，已用 pypdf 验证、提取正文，并目视核对缺陷案例所在页。

## 1. OATest：优化模式必须放到真实上下文中检验

**Optimization-Aware Test Generation for Deep Learning Compilers**，Qingchao Shen 等，**ICSE 2026**。[原文入口](https://arxiv.org/abs/2511.18918)，[原始 PDF](https://arxiv.org/pdf/2511.18918v1)，[本地 PDF](01_OATest_ICSE2026_2511.18918v1.pdf)。

- **具体困难：** 优化只在特定图结构下触发，缺陷还可能要求额外上下文。随机合法图未必触发目标优化，原有单元测试也未必覆盖新的上下文。把两者拼接时，又必须同时满足数据类型、shape 和数据依赖约束。见 §2.2、§3.2，PDF 第 3、5–6 页。
- **直接案例：** 已融合算子模式与上下文中的 `R.call_tir` 结合后，TVM 的 `MergeCompositeFunctions` 因缺失类型检查而访问空指针。模式或普通种子图各自不足以暴露问题。见 §4.2、图 5，PDF 第 8 页，TVM #17120。
- **方法覆盖：** 从已有优化测试提取模式，嵌入不同图上下文；优先复用兼容边，不满足约束时增加连接节点，再用崩溃和差分结果判定缺陷。实验对象是 TVM、ONNXRuntime。见 §3，PDF 第 4–6 页。
- **边界：** 这是编译器优化测试方法，不负责选择最快融合方案，也没有证明所有输入上的等价性。§5.2 提到的学习式融合、资源约束下的自适应融合和形式验证属于后续方向，不能写成已实现能力。见 PDF 第 10–11 页。

## 2. HirGen：优化顺序和表示变化会改变正确性风险

**Fuzzing Deep Learning Compilers with HirGen**，Haoyang Ma 等，**ISSTA 2023**。[原文入口](https://arxiv.org/abs/2208.02193)，[原始 PDF](https://arxiv.org/pdf/2208.02193v5)，[本地 PDF](02_HirGen_ISSTA2023_2208.02193v5.pdf)。

- **具体困难：** 单个算子和单道优化支持某种输入，不代表它们的组合也成立。不同 shape、dtype、算子连接和函数组织，会使同一数学计算进入不同编译路径。见 §3.1–3.2，PDF 第 3–5 页。
- **直接案例：** `FirstOrderGradient` 改写常量属性后，后续 `FuseOps` 沿用过严的标量检查，导致原程序能编译、优化后反而失败。见 §5.2.2、§5.3，PDF 第 8–9 页，Bug 10；这是组合兼容性缺陷，不能误写成实测性能退步。
- **方法覆盖：** 按算子与 dtype、shape、连接边的覆盖生成图；改写函数调用但保留计算语义，再比较原始、优化和改写版本的结果与执行状态，也比较 CPU/GPU。见 §3.1.3、§3.3，PDF 第 4、6 页。
- **边界：** 主要验证 TVM，跨编译器推广仍需实现；差分误差还可能来自平台精度或语义差异，需要判断，不能直接等同于编译器缺陷。它提供反例检测，不提供完整形式证明或最快融合搜索。见 §6，PDF 第 10–11 页。

## 对融合生成论证的价值

两篇共同支撑的是：**融合不是对局部代码的孤立修改，正确性取决于跨算子约束、外围上下文及优化组合；因此验证证据也要覆盖这些交互。** 这是由上述案例归纳出的挑战，不是“现有方法都不能融合”。

当前 workflow 的 case 评测、版本记录和反馈迭代能积累具体反例；但不能据此宣称已具备这些论文的结构覆盖、优化组合测试或形式等价证明。两篇均不是专门生成高性能融合算子的 Agent，也不直接证明本项目优于其他方法或解决了 NPU 特有难题。

版本说明：OATest 的 arXiv 摘要与本次下载 PDF 的缺陷统计不同，本文不混用统计数字；涉及案例和方法的定位均以本地 PDF 为准。本轮只下载、阅读，未复现实验。
