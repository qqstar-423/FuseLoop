# 等价性与测试：EAGLE / DocTer 阅读笔记

核对日期：2026-09-25。页码均指本地 PDF 页码。两篇都是深度学习库测试研究，不是融合算子生成或性能搜索论文。

## 1. EAGLE：实现变了，结果是否仍然正确

**论文：** *EAGLE: Creating Equivalent Graphs to Test Deep Learning Libraries*，Jiannan Wang、Thibaud Lutellier、Shangshu Qian、Hung Viet Pham、Lin Tan，ICSE 2022，13 页。[官方 PDF](https://www.cs.purdue.edu/homes/lintan/publications/eagle-icse22.pdf)｜[本地 PDF](01_EAGLE_ICSE2022.pdf)｜[作者代码](https://github.com/lin-tan/eagle)

**做法：** 人工从 API 文档和历史 bug 提炼 16 条等价规则，在同一库中构造功能等价、实现方式不同的计算图；生成符合约束的输入，执行并比较结果。它主要解决“不崩溃，但悄悄算错”的检测问题。

| 可引用证据 | 位置 | 能支持什么 |
|---|---|---|
| 优化前后应保持功能等价；浮点计算允许合理误差 | §3.1、§3.1.1，PDF 3–5 页；表 1 规则 1 | 代码可执行、公式看似等价，仍需验证实际数值行为 |
| time-major / batch-major 变换后，双向 RNN 错误地反转了 batch 维度 | §1.1，PDF 2 页，图 1 | 数据布局改变时，维度含义与上下文必须保持一致 |
| 优化后的 `complex64` 除法溢出；稀疏实现的底层函数误假设存储按行连续 | §5.2，PDF 8 页，图 4、5 | 类型、数值范围与存储假设会造成静默错误 |
| 固定随机种子，按绝对及相对容差比较；考虑不同输入及配置 | §3.3–4，PDF 6–7 页 | 测试需要明确比较口径，不能只看能否运行 |
| 两个等价实现若共享同一 bug，仍可能比较一致；规则也需要人工设计 | §6，PDF 10 页 | 差分测试是证据，不是完整正确性证明 |

**实验口径：** TensorFlow 和 PyTorch 上构造 6,861 对图，检出 25 个 bug，13 个此前未知，其中 9 个已确认或修复；优化类检出 10 个 bug。不能把这些数字当成融合内核错误率。表 2、图 4/5 已可视核对。

**与我们任务的关系：** 我们已有参考程序，不能照搬 EAGLE 的“缺少预期输出”作为项目现状。可迁移的重点是：融合、拆分和布局变化后，应在约定输入范围与容差下继续满足原计算的语义；给定 case 通过只覆盖已测情形。可考虑用布局、类型及边界输入的等价关系补测，这是本项目的延伸方向，不是 EAGLE 对本项目的实验结论。

**不能推出：** EAGLE 没有解决融合边界选择、tiling、资源分配或性能最优；也没有证明任何图变换都合法。本项目现有精度检查不能写成已经具备 EAGLE 式自动等价图测试生成。

## 2. DocTer：测试输入也需要理解算子约束

**论文：** *DocTer: Documentation-Guided Fuzzing for Testing Deep Learning API Functions*，Danning Xie 等，Lin Tan 为共同作者，ISSTA 2022，13 页。[官方 PDF](https://www.cs.purdue.edu/homes/lintan/publications/docter-issta22.pdf)｜[本地 PDF](02_DocTer_ISSTA2022.pdf)

**做法：** 从少量人工标注的 API 文档学习约束提取规则，抽取结构、dtype、shape、合法值四类约束；按参数依赖顺序生成输入，并覆盖符合约束、违反约束及边界情况。

- **约束与依赖：** §2.2–2.4，PDF 5–7 页。例子包括多个参数类型相同、张量维度由另一参数决定。表 1 已可视核对。
- **边界测试：** §2.5，PDF 7–8 页。包含零值、零尺寸、空结构等变换；有效输入用于深入执行主体，非法输入用于测试输入检查。它主要检测严重崩溃，不负责证明数值等价。
- **结果和边界：** §4.1、§4.3–4.4，PDF 8、10–11 页。提取约束的精确率为 85.4%；检测 94 个 bug，无约束基线为 59 个。符合所提取约束的输入平均只有 33.4% 正常通过，论文指出文档不完整仍是限制。

**可迁移的启示：** 融合测试不能只随机造几个张量，应围绕任务允许的 shape、dtype、数值范围及参数关系组织覆盖；文档也不能直接当作无误的完整规格。这里只支持测试设计的重要性，不支持“我们已经自动覆盖这些情况”或“加入该方法即可保证正确”。

## 3. 可提供给主文档的一句话

**挑战：融合会改变计算组织，但必须在多种输入和实现条件下保持原有语义；少量样例正确，不能证明优化始终正确。**

这是根据两篇论文对融合任务作出的归纳。现有参考实现与精度检查提供验证基础；更系统的约束覆盖和等价关系补测属于后续增强，不应写成已有实现。
