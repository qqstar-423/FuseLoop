# Stage1.5：Jev 融合方案选择（精简计划与修改记录）

本文件记录已接入的 Stage1.5：根据算子需求和当前硬件，为融合方法评分，选出前 n 个组成 **JSON 融合算子库**，作为后续实现与优化的基础。本轮只补充文档。

阶段顺序：**Stage1 需求分析 → Stage1.5 Jev 融合方案选择 → Stage2 首版实现**。后续语义退出和方案审查见[已确认的精简计划](<workflow_fusion_selection_semantic_exit_design.md>)。

## 前提：先把融合方法整理成完整选项

原始说明来自 `knowledge/fusion_method.md`，已整理为 `knowledge/fusion_options.json`，包含以下 10 类、24 个细化变体。

| 方法 | 主要方向 | 变体数 |
|---|---|---|
| F1 算子拆分／半融合 | 拆开计算与后处理，分别优化；也可在分区内部融合 | 3 |
| F2 垂直融合 | 将有先后依赖的计算融合，如 Conv → Sigmoid | 3 |
| F3 水平融合 | 合并相互独立的计算分支 | 2 |
| F4 输入／输出融合 | 共享输入、共享生产者结果或一次产生多个输出 | 3 |
| F5 混合路由 | 按 shape、dtype 等合法属性选择不同实现 | 3 |
| F6 跨核片上共享流水 | 在硬件明确支持时，通过片上共享数据衔接不同阶段 | 2 |
| F7 拆分与融合协同优化 | 搜索合适的拆分位置和融合分组 | 2 |
| F8 计算与访存联合融合 | 联合安排计算与访存子图的流水 | 2 |
| F9 深度融合 | 融合更长的依赖链或更大的计算区域 | 2 |
| F10 多设备通算融合 | 在多卡或多节点间重叠计算与通信 | 2 |

每类不仅有名称，还包含适用计算图、case 特征、硬件前提、执行组织、数据流、收益、风险、具体变体、实现检查项及可组合方法。Jev 对 **10 个大类分别评分**，24 个变体作为详情参与判断，不单独评分。

## Stage1.5 的输入与处理

下文 `<work>` 表示本次算子任务的工作目录。

| 输入 | 内容 |
|---|---|
| `knowledge/fusion_method.md` | 原始融合方案说明，读取正文 |
| `knowledge/fusion_options.json` | 上述完整候选目录 |
| `<work>/fusion_requirements.en.json` | Stage1 新增的英文需求摘要：算子语义、case 分组、精度要求、实现约束和用户优化方向 |
| `<work>/device_info.json` | 本次运行的硬件信息，如芯片、核数及片上存储容量 |

Stage1 继续保留完整 `ANALYSIS.md`；其文件指纹参与结果复用检查。实际提交 Jev 的需求来自英文摘要，程序根据请求容量给 Stage1 分配摘要大小，绝对上限为 6000 UTF-8 字节。

处理顺序：

1. **准备英文材料**：复用现有 Kerminal 翻译所有非英文内容，包括方法原文、选项详情、需求和硬件描述。保留 JSON 结构、方案 ID 和数值，再校验英文及请求大小。
2. **Jev 评分**：程序按 `model / state / questions` 组织请求，每个方法对应一个 `noul` 问题，得到 0～1 的适用性概率。
3. **程序选前 n 个**：检查 10 类方法都有合法概率，按概率降序排列，同分保留目录顺序。`config.yaml` 的 `fusion_selection.top_n` 控制 n，默认 3，可设 1～10。
4. **保存并进入 Stage2**：程序保存全量排序和前 n 个完整候选，Stage2 按最高概率方案开始设计首版。

概率表示“当前硬件和需求下，该方向可行且值得探索”的初始估计，各项独立，**不要求总和为 1，也不是实测加速比**。程序不额外设置概率门槛；硬件能力仍须核实，不能把共享 L2 Cache 直接当作 DSM，也不能因为单 kernel 就默认更好。

## 输出保存在哪里

| 输出 | 内容 |
|---|---|
| `<work>/fusion/fusion_library.json` | 前 n 个候选，即初始 JSON 融合算子库；每项包含排名、概率和完整方法详情 |
| `<work>/fusion/ranking.json` | 全部 10 类方法的概率及排序 |
| `<work>/fusion/jev_request.json`、`jev_response.json` | 实际英文请求和 Jev 原始响应 |
| `<work>/fusion/translation/` | 翻译前材料、英文材料、校验指纹及翻译记录 |

方案库还记录输入来源、文件指纹和 Jev 配置等追溯信息，不保存密钥。发送给 Jev 的内容全部为英文；交给后续节点的方案详情保留原目录的可读说明。

这里要区分：`knowledge/fusion_options.json` 是**所有方法的固定目录**；`fusion/fusion_library.json` 是**本任务筛出的初始候选库**；`develop/iterN/fusion_library.json` 是**实现节点记录本轮实际选择的版本**。初始候选库本身不包含本轮 `selection`，后续版本不得改写原 Jev 概率，新增未评分方案使用 `null`。

## JSON 融合算子库给哪些节点

| 节点 | 如何使用 |
|---|---|
| Stage2 | 优先采用最高概率方案；若有明确硬件或框架限制，记录依据并选择后续可实现候选 |
| Stage3 | 结合候选概率、Stage9 意见和真实评测选择本轮实现，记录选择依据 |
| Stage7 | 对照候选数据流和资源需求，分析当前实现的性能瓶颈 |
| Stage8 | 围绕瓶颈搜索候选方法的实现路径，核实硬件与框架支持 |
| Stage9 | 综合概率、选择依据、历史尝试和实测趋势，决定保留、局部调整或更换方案 |

上述五个节点都收到初始库。后续的真实精度与性能证据优先于初始概率；Stage3 的选择依据与自测报告分开，并继续传给 Stage7、8、9，具体规则沿用语义退出方案。

## 一个具体的 JSON 示例

假设任务是 **Conv + Sigmoid**，case 包含不同 shape，当前硬件信息显示 UB 为 **248 KB**，且尚未确认跨核片上共享能力。下面假设 Jev 将 F5、F2、F1 排在前三，配置 `top_n = 3`。

**数字仅用于演示，不是真实 Jev 评分或实测结果。** 以下为 `fusion_library.json` 的精简节选，省略追溯字段和方法的其他详情；真实文件保留完整方法与变体。

```json
{
  "schema_version": 1,
  "total_methods": 10,
  "top_n": 3,
  "candidates": [
    {
      "rank": 1,
      "probability": 0.88,
      "method": {
        "id": "F5",
        "name": "Hybrid Routing",
        "name_zh": "混合路由／按 shape 分发"
      }
    },
    {
      "rank": 2,
      "probability": 0.81,
      "method": {
        "id": "F2",
        "name": "Vertical Fusion",
        "name_zh": "垂直融合／单 kernel 全融合"
      }
    },
    {
      "rank": 3,
      "probability": 0.73,
      "method": {
        "id": "F1",
        "name": "Kernel Fission / Partial Fusion",
        "name_zh": "算子拆分／半融合"
      }
    }
  ]
}
```

在这个例子中，Stage2 首先考虑 **F5**：按合法 shape 属性选择实现，例如部分 shape 用 F2，将 Conv 的结果在片上传给 Sigmoid；其他 shape 用 F1，将计算和后处理分开调优。哪些 shape 适合哪条路径、分界值取多少，须由实现与评测确定，Jev 的 0.88 不提供这些答案。

0.88、0.81、0.73 分别表示 88%、81%、73% 的独立适用性估计，可以同时较高；F5 也可以组合 F1/F2。其余七类及概率仍保存在 `ranking.json`，没有因落选而丢失。

## 恢复规则与本次修改范围

输入及评分配置一致时，复用已校验的翻译和评分结果；只修改 n 时从已有全量排序重新取前 n 个。输入发生变化时重新评估。翻译失败、请求超限、概率缺失或非法时停止，不进入 Stage2，也不使用过期结果冒充新结果。

已进入迭代的旧任务，若既无新增需求 JSON、也无 `fusion/` 目录，保留原流程并提示缺少候选库；已经开始新流程但材料不完整的任务须修复后恢复。

已落实的修改包括：Stage1 英文需求输出；融合方法 JSON 目录；Stage1.5 评分、翻译、排序和结果复用；配置中的 n、翻译超时及 Jev 连接参数；Stage2/3/7/8/9 的候选库输入；Stage1.5 独立 role 说明及 Stage1 → 1.5 → 2 路由、日志和恢复；README 与相关离线测试。翻译默认超时 240 秒，复用 `agents.kerminal.cli`，底层 Jev 客户端也检查英文输入。

Stage1.5 不写算子代码、不产生性能成绩，也不建立最佳实现记录。语义退出、P0/P1/P2、提升或退步达到 5% 的 knowledge 记录及最佳实现规则，继续按已确认的方案执行。
