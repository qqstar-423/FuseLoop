# 程序的语义退出与融合方案审查（完整版）

本版完整说明已讨论的方向、节点间材料传递及实际案例依据，不包含实现代码或 JSON 接口细节。以用户确认的[精简版](<workflow_fusion_selection_semantic_exit_design.md>)为准，末节补充已落地的记录位置和窗口规则。

## 一、修改范围

本次主要调整程序退出条件，以及退出前对融合方案的审查方式。保留已有 stage 的主流程、失败处理、P0/P1/P2 修改意见和最大迭代上限；补充 stage3 的融合方案选择记录，并传给 stage7、8、9。

原来的要求是：stage6 性能达标后，如果不是单 kernel 真融合，stage9 就继续要求修改。新的方向是：以正确性和实测性能决定方案是否值得保留，以程序的累计提升条件决定退出，不再把单 kernel 或零 HBM 中间读写作为统一退出门槛。

合法性要求仍保留。允许多 kernel 或部分融合，不代表可以改变算子语义、使用旧输入结果或依赖错误计时获得成绩。

## 二、前置的 JSON 融合算子库

沿用前面约定：stage1.5 使用 Jev，结合已有融合方法、当前硬件和 stage1 的需求分析，对候选方案给出概率。程序选取前 n 个作为初始 JSON 融合算子库，n 可配置；stage2 从最高概率的可执行方案开始实现。

后续 stage3 读取方案库及概率，并更新本轮实际选择、尝试记录和新发现的方案。已有 Jev 概率保留；新增方案尚未评分时明确标记，不能由写代码的 agent 编造概率。

方案库用于帮助选择，不是永久白名单。stage3 找到新的有效方案，应允许它接受同样的精度和性能验证。已经获得的可信实测结果比最初的概率更有决定力。

本版不重新展开方案分类、概率接口或 stage1.5 的实现。

## 三、前提：程序记录性能最好的实现

只有完成有效性能评测后，才将实现纳入最佳候选比较。记录以下内容：

| 内容 | 需要保存的信息 |
|---|---|
| 算子实现方案 | 实际采用的计算方式和主要实现选择 |
| 融合方案 | 哪些步骤融合、哪些拆开、是否有按 shape/dtype 的不同路径 |
| 性能指标 | avg_speedup、HAP 及对应的逐 case 结果 |
| 评测材料 | 性能报告地址及对应精度结果 |
| 实现文件 | 与该次评测对应的完整实现目录，后续修改不能使这个版本丢失 |

选择标准已确定：**精度通过且全部 case 达标的实现优先，再按 avg_speedup 选最优。**HAP 保留用于分析，不改变这个主排序标准。

例如，一个实现平均加速比更高，但仍有 case 未达标；另一个平均略低但全部达标，最终应优先选择后者。若所有实现都未达标，不能把其中平均最高者报告为“全部达标”。

编译失败、精度失败、无效计时或缺少完整性能结果的实现，不因自测成功或文字报告评价较好就进入最佳记录。

入库还须给定 case 和同 shape 更换数据的连续调用自测通过，并确认代码、融合方案、自测及正式评测属于同一版本。采用不同计时口径或计时有疑问的历史成绩，必须按当前口径重测后才能进入最佳记录及 x/y 窗口。

## 四、场景1：每个 case 的 speedup 都 ≥ 1

达到这个条件时不立即退出，继续优化。

如果 x 次有效性能迭代的累计提升小于 5%，程序选择已经记录的最佳达标实现，交给 stage10 总结，退出迭代。x 在配置文件中设置。

尚未满足退出条件时，保留 stage6 → stage9 → stage3 → 下一轮 stage4。stage9 根据真实瓶颈提出优化意见，不能因为当前实现包含多个 kernel，就把“继续合并成单 kernel”作为必做任务。

stage10 接收的代码和评测结果必须属于同一版本，不能拿最佳轮的成绩描述最后一次尚未评测的修改。旧的融合退出判断不能绕过 x 次窗口，也不能否决已经满足新退出条件的合法实现。

## 五、场景2：并非每个 case 的 speedup 都 ≥ 1

保留原流程：stage6 → stage7 → stage8 → stage9 → stage3。

stage9 综合以下材料，动态决定下一步是否更换融合方案：

- stage7 对当前瓶颈和未达标 case 的分析。
- stage8 找到的优化建议。
- stage3 写的《融合方案选择决策依据.md》。
- 当前和历史的可信精度、性能结果。

如果连续 y 次有效性能迭代的累计提升小于 5%，stage9 重点重新比较已输入的 JSON 融合算子库及概率，并查看未达标 case 的历史 speedup、距 1 的差距及改善趋势。y 可配置，输出的修改意见仍使用 P0/P1/P2。

**停滞触发重新审查，不直接触发强制切换。**stage9 可以决定保留方案并做局部优化，也可以在有证据时更换方案。慢 case 的趋势辅助审查，不替代 avg_speedup 的 5% 窗口指标。

### 少数 case 未达标时怎么判断

只有一两个 case 慢，可能是方案不适配，也可能是对应 shape 的分块、尾块、布局、固定开销或精度路径问题，不能仅凭未达标数量作结论。

| 观察到的情况 | 审查方向 |
|---|---|
| 大多数 case 已达标，慢 case 集中在特定 shape/dtype | 优先检查相应实现分支，考虑局部修改。 |
| 平均加速比提升很少，但未达标 case 持续接近 1 | 当前方向可能仍有效，不应只凭平均停滞换方案。 |
| 多轮局部修改无效，瓶颈来自当前分区或数据流限制 | 对照方案库，考虑更换能解除该限制的方案。 |
| 不同 shape 适合不同路径 | 可以考虑按合法的 shape/dtype 条件选择实现，再做完整验证。 |

没有证据时，不预先认定“融合方案出问题的概率很小”；实际例子支持的是“先定位再决定”，而不是一个固定的概率结论。

## 六、stage3 分别输出哪些材料

stage3 是实际实施节点。写代码前读取 JSON 融合算子库及 Jev 概率，结合 stage9 的意见和已有实测结果作出选择。

### 1. 本轮 JSON 融合算子库

记录实际选择的方案、尝试情况及新发现的方案，保留已有概率的来源。方案被选中、被实现、被自测和被正式评测是不同事实，不能在尚未验证时直接标为性能有效。

### 2. 《融合方案选择决策依据.md》

这是 stage3 自己在实施过程中写出的决策说明，应简短回答：

- 这轮选择或保留了哪个融合方案？参考了哪些概率和证据？
- 针对哪些 case 或 shape/dtype 类别？
- 实际改了什么？只是分块/变体调整，还是改变了融合结构？
- 为什么预计这些改动能解决问题？
- 如果没有选最高概率方案，或偏离 stage9 的建议，理由是什么？

需要区分“已经完成的修改”与“预计获得的收益”。不能把准备做但未实施的建议写成已经完成，也不能把预计效果写成实测结论。

### 3. 自测报告

自测报告记录输入给 stage3 的 case 由它实际执行后的结果：测试范围、通过或失败、错误与相关现象。没有运行的 case 不能写成通过。

根据现有实现暴露出的缓存问题，增加一项明确检查：**同 shape、更换输入数据、权重或偏置，连续调用，结果仍应对应当前参数。**它属于自测内容，不需要增加工作流节点。

方案选择依据回答“为什么这样写、实际怎么改”，自测报告回答“这些测试实际跑出了什么结果”。两份文档分开，正式性能优劣仍由 stage6 的有效评测决定。

## 七、选择依据如何传给其他 stage

| 接收节点 | 如何使用《融合方案选择决策依据.md》 |
|---|---|
| stage7 | 对照选择理由与实际代码，检查预期瓶颈是否被解决，分析未达标 case。 |
| stage8 | 了解已经采用和尝试的方向，有针对性地搜索改进方法。 |
| stage9 | 综合选择理由、实际改动、瓶颈和性能，决定下一轮保留还是更换方案。 |

各节点读取的必须是与当前被评测代码对应的文档。stage9 给出下一轮意见后，stage3 执行并输出下一版选择依据，供后续评测和审查使用。

首轮尚无 stage3 产物时沿用已有设计材料，不改变首版开发流程。

## 八、P0/P1/P2 和审查原则

P0/P1/P2 保留，只取消“融合方向永远最高优先”的固定要求。优先解决正确性和未达标 case，再提升整体性能。

stage9 审查时注意三点：

1. 判断修改是否有证据、是否针对实际瓶颈，而不是仅看是否选了最高概率方案。
2. stage3 找到新方案并取得可信的更好结果，不因其偏离最初计划就强制改回。
3. 单 kernel、多 kernel、中间经过 HBM 都是实现特征，不能单独用来判定方案优劣或决定退出。

若 stage3 没执行某条建议，选择依据应交代实际尝试和原因，供 stage9 判断是合理调整，还是任务没有完成。不能将“没实施”误判为“方案实施后没有收益”。

## 九、实际输入和 v1/v2 带来的结论

此前阅读了旧 PyPTO 输入定义、golden、24 个 case，以及两版实际 dispatcher 加载的实现和历史报告；原材料现由用户另存备份。24 个 case 包含 11 个 float16、7 个 float32、6 个 bfloat16，覆盖不同卷积核、步长、膨胀率、通道和空间尺寸。

以下是旧 PyPTO 材料的静态观察，未重新执行 NPU 精度或性能评测，也不是 Triton 成绩。历史趋势仅用于说明审查思路，不作为当前“最佳有效实现”的直接入库依据。

### 结论1：平均停滞不一定意味着慢 case 没有进展

v2 的历史记录中：

| 指标 | iter3 | iter6 |
|---|---:|---:|
| avg_speedup | 2.684 | 2.724 |
| case3 speedup | 0.683 | 0.977 |

平均提升约 1.5%，但 case3 已明显接近达标。这支持场景2由 stage9 同时看未达标 case 的趋势，不能只因平均提升小于 5% 就强制换方案。

实际代码也有 shape 对应的不同实现分支，例如小通道的 KB16/KB32、特定 7×7 stride=2 的 compact-G，以及另一类 shape 的 TM128。这些说明“继续当前融合方向、局部调整实现”是实际存在的选择。但单看代码不能证明某项修改带来了多少性能提升。

依据：用户备份中的 v2 `ITER_REPORT.html` 与 c2 实现的 shape 分支。

### 结论2：自测需要验证连续调用时使用的是当前数据

两版实际入口都存在按 shape/config 缓存预处理张量的逻辑。缓存命中时直接取出旧张量，权重和偏置的预处理只在首次未命中时进行。

因此，相同 shape 更换权重或偏置后，代码仍会复用旧的预处理值；对经过复制或 padding 的输入也有同类问题。已有单组数据的测试通过，并不足以验证这种调用方式的正确性。

对计划的补充就是第六节的连续调用自测。缓存问题没有在本轮修复，也不能据此声称两版已经通过新增检查。

依据：用户备份中的 v1、v2 c1 实现的缓存读取逻辑。

### 结论3：旧成绩不能证明半融合一定优于全融合

v1 报告记录了 avg_speedup 约 4.56x，v2 记录了约 2.87x。但 v1 报告同时明确指出旧计时存在 kernel 耗时取均值、离群过滤可能排除较慢 kernel 的问题。

因此，需要修正之前仅根据这两个数字作出的判断：它们不足以证明半融合的真实执行性能更好，也不能直接作为新工作流选择最佳实现的依据。

两版需要先确认正确性，再按当前一致的完整评测口径重新验证。只有可信的新结果才能参与最佳候选和 5% 停滞判断。本次没有重测，因此不对两版真实快慢作结论。

依据：用户备份中 v1 `FINAL_REPORT.md` 对计时问题的说明。

## 十、统一口径与实现落点

- 累计提升使用同一窗口开始和结束时的最佳 avg_speedup 比较，不把逐轮百分比相加，也不把退步后的恢复当成新的突破。
- 编译失败、精度失败和无效性能评测不计入 x/y，仍按原失败流程处理；最大迭代上限保留。
- 用于比较的性能结果必须采用一致的口径；正确性或计时有疑问的历史成绩不能直接进入最佳记录。
- n 默认 3；x/y 分别配置在 `workflow.semantic_exit.passed_window` 和 `underperforming_window`，默认均为 3。需要一份有效基线加 x/y 次有效成绩；达标状态切换重置连续窗口。窗口两端比较该状态的历史最佳 avg_speedup，恰好提升 5% 不触发停滞。

最佳清单位于 `<work>/selection/best.json`，记录实现方案、融合方案、HAP 原始指标、avg_speedup（另保留 avg_speed 别名）、报告和实现快照路径。每份有效成绩对应 `<work>/selection/records/iterN-指纹/` 的独立代码、报告、依据文件副本，避免后续修改或报告覆盖。首次有效性能评测前不生成最佳记录。

`selection/state.json` 维护有效样本索引及窗口；同一轮恢复不重复计数，同轮重测保留已有快照，但窗口只计最新的一次。同硬件、任务/case 集合、工具及 baseline/计时策略才可比较；实际 device_id 或固定 metadata 基准文件版本改变会另开比较组，同一口径下报告数值的正常波动不会另开分组。

Stage2/3 的本轮库写入 `develop/iterN/fusion_library.json`，保留初始 Jev 概率，新方案标记未评分。Stage3 独立输出《融合方案选择决策依据.md》。自测报告另附 `self_test_result.json` 和实际日志；程序将代码与这些文件绑定，后续改代码会使旧证据失效。首轮沿用 Stage2 的 `design_rationale.md` 作为选择依据。

Stage3/7/8/9 读取最佳记录和逐 case 趋势；Stage7/8/9 同时读取与代码对应的选择依据。语义退出或达到上限时，Stage10 使用最佳快照及同版报告，而不是最后一次未评测修改。没有合格记录时明确说明，不编造最佳实现。Stage9 原有提升/退步达到 5% 写入 knowledge、P0/P1/P2 及失败处理保留，包括语义退出当轮的知识记录。

### 单轮退步的处理与追溯

单轮涨跌继续比较本轮与最近一轮 avg_speedup >0 的结果，变化百分比保留一位小数后判断 ±5%；这与 x/y 窗口比较历史最佳的累计提升是两种判断。

- 本轮全部 case ≥1 且退步达到 5%：Stage9 先分析退步实现并提交教训，程序再恢复同口径最佳达标快照，Stage3 从最佳基线继续修改。若同时满足语义退出，也先提交知识再恢复、总结。
- 本轮存在 case <1 且退步达到 5%：只记录退步教训，保留当前代码；不会因为历史最佳全部达标就回退。
- 无有效的本轮绑定或最佳快照时不自动恢复；恢复中发现快照损坏或代码被修改则中止，保留现场。恢复本身不新增评测，不覆盖原成绩。恢复后旧自测绑定失效，Stage3 修改后重新产出选择依据及自测。

两类停滞、退步分支和恢复完成均在 workflow/state 日志中用 `=====` 标注。停滞次数存于 `selection/semantic_events.json`：每个场景独立累计，新有效轮触发一次，同轮恢复不重复，与三次人工咨询计数独立。`selection/rollbacks/iterN/record.json` 保存退步处置、前后成绩、源快照、Stage9 决策及知识文件地址，`failed_impl/` 保留恢复前代码。恢复过程有断点记录，Stage3 重试不会再次覆盖已经开始的修改。

本轮已修改工作流并完成离线验证；未修复案例算子，也未重新运行 NPU 精度或性能评测。具体接口与文件用途见 README。
