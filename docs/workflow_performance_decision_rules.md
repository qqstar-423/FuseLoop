# 性能判断规则：代码现状与后续完善

记录当前三个判断。已补齐单轮经验比较的口径检查；后面的建议尚未实施。

## 1. 是否全部达标：看每个 case 的 speedup

正常性能评测中，全部 case 的 speedup **≥1** 属于场景1；只要一个 **<1** 就属于场景2。平均加速比大于1，不能代替每个 case 都达标。

报告还须包含完整 case，运行成功且耗时、加速比有效；缺报告、零分或评测错误先走异常处理。进入最佳记录还要求精度通过、代码与方案/自测证据对应。

“达标”表示这组测试全部不慢于基准，并不表示已经充分优化。

## 2. 是否记录经验：看单轮 avg_speedup 的涨跌

先找最近一轮均值为正、没有评测错误的报告，再确认两轮都包含完整有效的 case，并且**硬件、任务及 case、基准、计时方式、评测器及预热/重复次数一致**，才比较：

**变化率 =（本轮 avg_speedup ÷ 上一轮 avg_speedup − 1）×100%。**

程序先保留一位小数，再判断：

- 提升 **≥5%**：Stage9 总结原因，程序写入 `knowledge/proven_patterns.md`。
- 退步 **≥5%**：Stage9 总结原因，程序写入 `knowledge/regression_patterns.md`。
- 其余变化：不触发上述两类性能经验记录，正常轮次和账本仍保存。

记录经验不要求全部 case 达标。退步时，**本轮全部达标**才在记录教训后恢复最佳达标代码；仍有慢 case 就保留当前代码。自动恢复还须有本轮有效证据和同口径、校验通过的最佳快照。

**口径不一致或旧报告缺少口径信息：不计算本次涨跌，不写这次成功/退步经验，也不因表观退步触发回退。** 本轮报告完整有效时作为新基线；下一轮同口径再恢复比较。不会越过最近的异口径报告，去找更早的同口径成绩凑比较。当前报告本身无效时，仍走原异常处理。

口径保存在 `eval/iter<iter>/perf_result.json` 的 `comparison_context`；`comparison_context_stable` 说明测量前后是否一致。比较结论和原因保存在同目录 `perf_comparison.json`，日志以 `===== 性能比较口径检查 =====` 标出。旧报告不补造口径；断点恢复重新检查，不直接使用旧缓存结论。

恢复时若本轮工作报告丢失，但同一轮的归档快照完整、口径一致，程序读取归档报告重新判断，并记录实际来源；工作报告仍存在但损坏或缺少口径时，不偷偷换用另一份报告。

history 同步标明比较状态：`comparable` 为可比，`new_baseline` 为新基线，`unavailable` 为当前缺少可靠比较依据。不可比时 `avg_speedup_before`、`delta`、`improved` 为 `null`，本轮实际成绩继续保留。最佳记录原有的精度、自测和代码版本绑定要求继续保留；单轮涨跌检查不替代这些要求。

## 3. 是否停滞：看 x/y 次有效迭代内历史最佳提升多少

在同一评测口径、同一达标状态下比较：

最佳记录的分组也核对每个 case 的实际基准耗时。基准改变后使用新组的最佳和窗口，避免从旧基准组恢复代码；旧版缺少基准分组信息的记录保留为档案，须重新评测后再参与当前选择。

**累计提升 =（窗口结束时的历史最佳 avg_speedup ÷ 窗口开始时的历史最佳 avg_speedup − 1）×100%。**

- **场景1，全部 case ≥1：** 经过 x 次有效迭代，累计提升 **<5%**，Stage9 完成经验记录，程序交付最佳达标快照给 Stage10 并退出。
- **场景2，仍有 case <1：** 经过 y 次有效迭代，累计提升 **<5%**，沿 Stage7→8→9 重点审查方案。Stage9 结合慢 case 趋势决定是否更换，不强制更换、不因此直接退出；最大迭代上限仍有效。

x 是 `workflow.semantic_exit.passed_window`，y 是 `workflow.semantic_exit.underperforming_window`；5% 阈值目前固定。

窗口需要 **1份基线 + x/y份有效成绩**。有效不等于必须提升：评测合格的退步轮也计数，无效轮跳过。同轮恢复不重复计数；达标状态切换重置窗口计数，但各状态的历史最佳保留，可能来自窗口之前。

这里不累加每轮涨跌，恰好提升5%不算停滞，也没有“累计下降5%就记录经验”的规则。例如 `2.0→1.5→1.8`，最后一轮提升20%，会触发第2条；历史最佳仍为2.0，第3条累计提升为0%。

日志中的“第几次进入场景”和人工咨询的“三次触发”另行计数，都不是 x/y。HAP 保留供分析，不用于上述三个阈值判断。

## 是否符合原定场景

**总体符合。** 全部 case 不慢于基准作为底线，达标后继续优化，停滞再交付最佳；少数 case 未达标时保留探索空间，由 Stage9 看趋势决定是否换方案。这也避免仅因多 kernel 就强制修改。

## 后续建议（尚未实施）

1. **对接近1的 case 复测。** 目前0.99和1.01会切换场景、重置窗口；测量波动可能影响判断。建议先确认结果稳定，再判是否达标，保留“不慢于基准”的要求。
2. **区分“从退步中恢复”和“刷新最佳”。** 两者都可总结经验，但应标明区别；上面的1.5→1.8不能描述成超过历史最佳2.0。
3. **用实际任务检验 x/y 和5%。** 特别关注少数慢 case 持续改善的任务；当前已将趋势交给 Stage9，不能只看平均提升就判定融合方案无效。
