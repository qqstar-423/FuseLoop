# Stage9 Review（按场景）

**定位：纵观迭代过程的技术 leader，判断问题、指引方向、协调分歧，把下一轮目标交给 Stage3。**

本版按已接入的**场景裁剪和人类参与**整理，保留原有路由、最佳实现和知识记录规则。人工行为按[已确认方案](<workflow_human_review_design.md>)执行；真实模型与 NPU 联调效果仍须实跑验证。

裁剪后，通用规则保留需求、硬件、正确性、证据绑定、P0/P1/P2 和输出协议；任务与默认阅读材料按场景选择。完整资料保留版本、路径、用途和读法供回查，裁剪不删除证据。人工意见始终放在显著位置。

最终决策统一写入 `knowledge/stage9/<iter>/<请求编号>/decision.json`，程序校验后合并本轮账本并保存经验；原始决策、调用前快照及实际 prompt/role 留档。咨询调用只写问题，收到反馈或超时后才走最终交接。

2026-09-25补充：本轮评测结果写入 `ledger.evaluation_summary`，下一步计划仍为 `direction`。性能场景逐一提交最慢case的 `ledger.case_analysis`，程序校验覆盖后按case更新tracker并保留旧轮；旧文件限制和 regression/no_change 标签不能直接否决新计划。详见[实例检查与修复](workflow_history_review_fixes.md)。

**建议改为程序定义的 v2 任务单：** Stage9先读本次 `decision_schema.json`、`decision_template.json`、`case_catalog.json`，再逐条填任务编号、目标case、实现映射证据、每文件操作/位置/方法与验收。允许文件由 changes 自动汇总，禁止文件全局一份；每轮任务另存 ledger.action_plan，Stage3看到完整任务。direction和慢case的next_action只供理解。校验不合格同轮最多修正两次，首次加修正共三次，第三次仍失败不下发、不写本次经验、不增加性能轮次；原输出/错误留档，两次修正分别在retry1、retry2。恢复也复核，旧任务先交Stage9重填v2。详见[任务单与case7示例](workflow_stage9_plan_v2.md)；程序不保证模型给出的路由解释或方法一定正确。

## 1. 编译失败

**路由：Stage4 → Stage9 → Stage3。**

- **输入：** Stage4 的 build.log；Stage2/3 的代码、自测报告和日志；上轮建议；未裁定的 question.md（如有）。
- **目的与工作：** 区分安装/import/环境问题和代码编译问题，检查上轮改动，裁定技术异议，明确修什么、哪些文件不能动。
- **输出：** history.json 中的失败经验、修复方向、文件范围及 P0/P1/P2；有裁定时形成错题本内容。没有本轮性能成绩，不据此新增性能涨跌经验或更新最佳记录。
- **重合：** Stage3 已自测、排错，Stage4 已验证并记录编译错误；Stage9 重点是综合归因、定修复方向。
- **裁剪与人工参与：** 只默认要求编译归因、修复计划及相关历史；不要求慢 case 分析、性能归因或换融合方案。主动意见结合编译问题转成 P0；超出本场景的方向保留并说明后续如何处理，不强行打断 Stage4。

## 2. 精度失败

**路由：Stage4 → Stage5 → Stage9 → Stage3。**

- **输入：** Stage5 精度结果和失败 case；Stage4 编译日志；Stage2/3 代码、自测及连续调用结果；case/golden 参考。
- **目的与工作：** 核对自测与正式精度差异，判断计算错误、边界输入、旧数据复用或环境问题；检查上轮建议落实情况，确定修复方向。
- **输出：** history.json 中的正确性问题、修复计划和 P0/P1/P2；有 question.md 则裁定并形成错题本内容。本轮尚无性能结果，不新增性能涨跌经验。
- **重合：** Stage3 做自测和精度排查，Stage5 做正式验证；Stage9 负责解释差异、协调修复。
- **裁剪与人工参与：** 重点保留失败 case、精度差异、自测和修复边界，不要求尚未产生的性能分析。主动意见经 Stage9 形成 P0，同时保留精度要求；有冲突须解释并给替代方案。

## 3. 性能评测与继续优化

当前达标标准是 **每个 case 的 speedup ≥1**。y 次有效迭代需要一份基线加 y 份有效成绩；失败和无效评测不计入，达标状态变化时窗口重新开始。

### 3.1 尚未全部达标，有效迭代不足 y 次

**路由：Stage4 → Stage5 → Stage6 → Stage7 → Stage8 → Stage9 → Stage3。**

- **输入：** Stage6 性能结果及 profiling；Stage7 瓶颈分析；Stage8 FIX_DIRECTIVE；Stage3 代码、选择依据和自测；上轮建议、历轮设计与经验、最佳记录和慢 case 趋势。
- **目的：** 判断本轮改动是否有效，选出下一轮最值得做的优化。
- **工作：** 检查上轮建议是否落实；分析最慢 6 个 case，回顾历轮收益和慢 case 改善；核对融合数据流与反作弊约束，决定保留、局部优化或有依据地换方案；有 question.md 时裁定分歧。

**可能输出的 knowledge 全部列在这里：**

- **knowledge/history.json：** P0/P1/P2（suggest_next）、修改方向和文件范围（ledger）、跨轮经验（insights）、当前瓶颈（bottleneck_now）、慢 case 追踪（worst_cases_tracker）、融合尝试（fusion_kernel_strategy）。程序填写的成绩 rounds 保留。
- **knowledge/proven_patterns.md：** 单轮平均加速比提升 ≥5% 时，Stage9 提供成功原因，程序追加。
- **knowledge/regression_patterns.md：** 单轮平均加速比退步 ≥5% 时，Stage9 提供失败教训，程序追加；原规则保留。
- **knowledge/tech_lead_pitfalls.md：** 有待裁定异议时，Stage9 提供裁定，程序追加，并回写原 question.md。

涨跌经验详细记录改动、原因、受影响 case、证据、适用条件及后续建议；程序补性能数字、对比轮次和报告路径。同一轮重复审查更新原记录；必须的分析缺失时停止 Stage9，不再写占位经验。

**重合：** 慢 case、profiling 和改动收益分析与 Stage7 明显重合；具体文件、改法和禁改项与 Stage8 重合。跨轮取舍、执行监督、争议裁定和每轮经验维护主要归 Stage9。

**裁剪与人工参与：** 优先读 Stage7/8 结论、当前选择依据及相关历史，必要时查原始 profiling；保留本轮知识记录要求。此时只接收主动意见，不自动求助；意见经 Stage9 形成 P0，再由 Stage3 记录落实。

### 3.2 尚未全部达标，有效迭代达到 y 次

**路由仍为：Stage4 → Stage5 → Stage6 → Stage7 → Stage8 → Stage9 → Stage3。**

**还要看提升幅度：** 窗口内最佳平均加速比累计提升 ≥5%，仍按 3.1 普通优化；只有 **<5%** 才触发重点审查，不能仅按次数判断。

- **输入：** 3.1 的材料，加上程序的停滞提示：窗口轮次、起止最佳平均加速比和累计提升。Jev 库此前已输入，此时要求重点比较。
- **目的与工作：** 判断方向是否值得继续。结合历史尝试、候选方法和慢 case 趋势，区分局部问题与结构性限制；即使平均停滞，慢 case 仍持续接近 1，也可以继续当前方向。
- **输出：** 沿用 3.1 的全部输出种类；明确“保留／局部优化／更换”的理由、目标 case 和下一步验证。停滞不等于单轮退步 ≥5%，不能混写成退步教训。
- **重合：** Stage7 已分析局部/结构性瓶颈，Stage8 已搜索替代方法；Stage9 重点做跨轮比较和最终取舍。

**裁剪与人工参与：** 第 1、2 次停滞仍由 Stage9 审查方向，并可接收主动意见；自动咨询启用时，第 3 次必须求助。该场景增加候选方案比较和慢 case 趋势，咨询时只要求写清难点、选项和推荐理由，收到回复或超时后才产出最终修改决策；等待与复议详见第 4 节。

### 3.3 全部 case 已达标，继续提升性能

**当前实际路由：Stage4 → Stage5 → Stage6 → Stage9 → Stage3。**

**保留当前跳过 Stage7/8 的路线。** 因此仍由 Stage9 做必要的性能分析，默认输入不使用本轮 Stage7/8 文件，即使目录残留旧文件也不当作新结论。

- **输入：** Stage6 性能及原始 profiling，Stage3 选择依据、自测，上轮建议、历轮设计与经验、最佳记录和 x 窗口；没有本轮新生成的 Stage7/8 结论。
- **目的与工作：** 与 3.1 同属普通优化：检查建议落实、本轮收益和进一步提升空间，提出下一轮方向、维护经验；不能因多 kernel 或 HBM 就强制换方案。
- **输出：** 与 3.1 相同，涨跌 ≥5% 和争议裁定仍按条件记录。程序将已接收决策中的总体结论、逐 case 分析整理为 `profile/<iter>/bottleneck_analysis.md`，标注 Stage9、轮次和决策来源，供 Stage3 读取；退出轮也保留。模型仍只提交 decision JSON，不额外写一份报告。
- **重合：** 职责上与 Stage7/8 相似，但本分支未执行它们，不能删掉 Stage9 的必要分析而无人接替。
- **裁剪与人工参与：** 保留必要性能分析和方向判断，移除“读取本轮 Stage7/8 结论”的强制要求。只接收主动意见，不触发未达标停滞求助。退出前也须处理待办意见；受既有退出条件或迭代上限限制无法执行时，明确记录原因。

退出由程序检查：满足 x 次有效迭代累计提升 <5% 后，Stage9 完成经验记录，程序复核最佳实现再交 Stage10。

**每轮统一一份报告：** 未达标路线保留 Stage7 原报告并标注来源，Stage9/3 读取它；达标路线由程序整理 Stage9 分析，Stage3 读取它。文件名始终不变，同轮复议覆盖同一文件，历轮报告各自保留。报告只展示已有分析和证据，不代表自动完成了全部原始 profiling 检查。

**单轮退步的分工：** 涨跌达到 5% 的知识记录仍由 Stage9 提供原因、程序落盘。本轮全部 case ≥1 且退步达到 5% 时，记录后由程序恢复最佳达标代码；Stage9 提前获知恢复计划，下一步建议应以最佳代码为基线。本轮仍有慢 case 时只记录、不恢复。恢复前后代码和对应报告均保留，Stage9 不负责执行代码恢复。停滞日志另记两个场景各自的累计进入次数，与人工咨询计数独立。

### 3.4 补充：零分、报告异常或评测崩溃

- **错误码或平均加速比为 0：** Stage4 → Stage5 → Stage6 → Stage9 → Stage3。输入性能错误、kernel CSV、代码及反作弊规则；先查异常或违规根因，输出修复计划，不按正常慢 case 优化处理。
- **进程失败且无报告，连续两次仍失败：** 程序停止在 Stage6，不调用 Stage9；排查后恢复评测。
- **已调整：** 零分提示先要求区分报告/采集故障与代码问题，缺报告不直接判为作弊。错误分支本身仍沿用原路线，更细的路由拆分留在待办。
- **裁剪与人工参与：** 任务限定为按实际错误及证据定位异常，不要求完整性能优化。运行中收到的主动意见先保存；不因零分或崩溃增加有效停滞计数，也不触发第三次停滞求助。

## 4. 人类参与后的 Stage9

### 4.1 主动介入：随时接收，在交付前生效

程序保存人的原话和意见编号，不打断正在执行的节点。下一次 Stage9 下发指令前加入原场景；已形成决策但尚未交付时收到新意见，先复议。Stage3 启动前和正式退出前都检查是否有未处理意见。

入口是另一终端运行 `tools/human_review.py --work-dir <work> --text "意见"`；纯提问加 `--kind question`，查看状态用 `--status`。`config.yaml` 的 `workflow.human_review.proactive_enabled` 和 `consultation_enabled` 可分别开关，默认开启。

**输入：** 原场景材料 + 人的完整意见/问题 + 先前决策（如有）。**输出：** 原有 decision.json，增加逐条 `human_responses`；实质方向明确列为 P0 并关联意见编号。Stage3 在选择依据及 `develop/<iter>/human_feedback.json` 说明落实情况，程序区分已处理和已执行。纯提问先答疑，等待指令不成为 P0；与精度或硬件冲突时解释原因和替代方案，不静默忽略。

### 4.2 第三次停滞：先咨询，再形成最终决策

**流程：Stage7 → Stage8 → Stage9 写问题 → 程序等待 → Stage9 复议 → Stage3。**

- **咨询输入：** 3.2 的证据、三次触发轮次和已有人工意见。Stage9 输出 `human_review/<iter>/<请求编号>/question.json`，程序校验并生成同目录 `问题文档.md`：难点、尝试、2～3 个选项及推荐理由。此时不提交最终账本或下发 Stage3。
- **程序等待：** 通知后计时 2 分钟；“请等待／等待一会儿”仅在原截止时间上加 10 分钟，一次咨询只延长一次。正式回复立即结束等待；超时按推荐方案继续，不冒充人工同意。
- **复议输入：** 人的全部回复、原问题及全部选项、原场景与完整证据清单；优先处理新增意见，有变化再补读材料。超时则明确注入“未收到人工意见”。
- **最终输出：** 沿用独立 decision 协议，人工实质建议列 P0，程序合并当前账本并记录应有的 ±5% 经验。同一评测复议不重复追加知识、不增加轮次或 x/y。

程序按新增有效评测计数，重跑/恢复不重复；咨询完成、全部达标或窗口提升恢复到 ≥5% 后清零。等待状态、原场景和截止时间持久保存；恢复沿用原时间。迟到回复转为主动介入；已结束任务不自动重开。

## 5. 修复范围与后续待办

1. **已接入：任务按场景裁剪。** `lib/stage9_scenes.py` 组合共享规则、当前场景任务和人工处理阶段，不再加载全套任务；输入也按需组织。
2. **已接入：保存并恢复原场景。** 利用状态中的失败原因及人工等待状态恢复原分支，避免等待后将编译/精度失败当普通性能优化；恢复沿用原截止时间。
3. **已修复：经验接收字段。** 程序直接消费本次 decision 的 proven_pattern / regression_pattern / pitfall，落盘详细经验与裁定，拒绝旧请求或缺失的必填分析。本轮触发的涨跌经验会完整列入 `decision_schema.json` 和 `decision_template.json`；`applicability` 用文字，每条经验 case 单独写 `explanation`，不能由账本中的解释代替。校验一次列出该经验内全部字段错误，`validation_error.json` 的 `errors` 及日志标明字段路径、下标和 case ID。同轮最多修正两次，第三次输出仍不合格就保留原历史、停止交付，不自动补写原因。
4. **已修复：旧账本保护。** Stage9 仅提交 ledger_entry；程序从调用前完整历史合并当前轮，保留旧 ledger 和硬指标。原有 insights 更新语义保留，历轮材料的阅读量仍可后续精简。
5. **已修复：本轮 JSON 格式与校验不一致。** 请求编号的固定值仅约束 `request_id`，不再因共享对象误传到总结、原因等文字字段。精度等错误场景的 `case_analysis` 只能省略或为空，具体原因保留在总结和修复任务；未触发的涨跌经验及无待裁定问题的 `pitfall` 不再列入本轮格式。接收时一次报告场景不适用字段和经验缺项，让 Stage9 完整修正；不自动删除分析或放宽必填经验。
6. **已修复：任务错误遮住文件错误。** 一次汇总多条任务冲突、字段缺项和多个文件路径错误。即使某条任务不完整，也继续检查其他可判断的任务和路径，把“漏查绑定源码”和“把 profiler 目录当文件”等独立错误一起反馈；结构损坏的部分只跳过依赖它的检查。诊断结果不能作为执行授权；所有原有校验通过后才交付。当前 `inspect` 任务也须列具体文件，按 case 检查时须包含绑定源码的核对；先浏览目录找到实际报告，不猜造路径。

实现范围和验证边界见[改动计划](<workflow_human_review_stage9_change_plan.md>)；其他 Stage9 优化见[TODO-002](<../TODO/todo_002_stage9_followups.md>)。代码接入不代表已验证真实模型的选项质量或 NPU 上的调优效果，这两项仍需实际任务检验。

## 6. 场景裁剪专项检查

- 检查实际传给 agent 的 role、prompt 和 request，覆盖六类场景；特意保留旧性能、Stage7/8 文件，验证编译/精度/评分异常/达标场景不会误读为本轮默认任务。
- 修复旧轮次的停滞或达标状态影响本轮分类的问题；停滞判断绑定当前评测轮次，明确的未达标路由不会被旧达标状态覆盖。
- 恢复优先使用已保存的原场景与路由，人工咨询不因当前 selection 暂时不可用而变成普通优化。
- 咨询只生成问题；最终复议才提交账本、人工 P0 和本轮应记录的经验。缺失输入明确标注，不假设 Stage7/8 已有结论。
- `log/workflow.log` 的 `[Stage9 场景]` 记录轮次、场景、阶段、请求编号、人工意见编号，以及实际 role/prompt/输入清单路径；可对照 `knowledge/stage9/<iter>/<请求编号>/request.json` 的 `default_inputs`、`missing_inputs` 检查。
