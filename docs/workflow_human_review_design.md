# 人类参与方案（已实现）

本方案已接入程序。人类通过两种方式参与：**主动导引方向**，或在反复停滞时由 **Stage9 主动咨询**。两种方式都先交给 Stage9 整理，明确将人的实质建议作为 P0，再交给 Stage3 执行。控制流程通过离线联调；真实模型与 NPU 上的效果仍需实跑验证。

## 1. 人类主动介入

**什么时候参与**：workflow 运行期间任意时刻，不需要等 Stage9 求助，也不要求已经性能停滞。

**怎么参与、如何生效**：

1. 人在另一个终端，通过 `python tools/human_review.py --work-dir "本次工作目录" --message "先保留当前融合方案，重点优化两个慢 case"` 提交，程序保存原话。纯问题加 `--kind question`；长意见可用 `--file 意见.txt`；`--status` 查看状态。
2. 程序接收并暂存意见，不强行打断正在运行的开发、编译或评测；在下一次 Stage9 下发修改意见前注入。如果 Stage9 已经给出意见，则重新交给 Stage9 复议。
3. Stage9 同时读取人的原话和当前代码、评测、融合方案等上下文，将人工方向明确写为 **P0（人工建议）**，说明具体修改目标，再交给 Stage3。不能只附在背景里，也不能悄悄降为 P1/P2。
4. Stage3 在下一版《融合方案选择决策依据.md》中说明采用了哪条人工意见、实际改了什么；后续用正式评测验证效果。

若人工意见与正确性或硬件能力冲突，Stage9 应解释原因并给出替代方案；反问先答疑，不擅自当作修改指令。下发指令或正式退出前检查是否还有未处理意见；受现有退出条件或迭代上限限制而不能执行时，在总结中写明原因，不静默丢弃。已结束的任务不因收到意见而自动重开。

## 2. Stage9 主动咨询

**触发条件**：场景2——仍有 case 的 speedup < 1，且连续 y 次有效性能迭代的累计提升小于 5%。**这个停滞条件触发第 3 次时，Stage9 必须主动寻求帮助**，不再由它自行决定是否求助。

计数口径：沿用现有滚动 y 窗口，每个新增有效评测轮次满足条件算一次；同一轮恢复、重跑 Stage9 不重复计数，窗口可以重叠，不要求累计 3y 次迭代。一次咨询处理完、全部 case 达标，或窗口累计有效提升恢复到 ≥5% 后清零；失败评测不计数。

**先生成明确的《问题文档.md》**，保存在 `<work>/human_review/<iter>/<请求编号>/问题文档.md`。`<iter>` 为实际评测目录名，如 `iter6`。终端醒目提示文件位置，提醒人及时阅读。文档保持简短，包含：

- **问题与难点**：当前融合方案、哪些 case 未达标、已经尝试什么，以及这次需要人判断的具体问题。
- **判断依据**：3 次停滞触发的轮次、最佳 avg_speedup/HAP、慢 case 趋势；附实现、性能报告和方案依据的路径及简短读法。
- **多个选项和推荐方案**：给出 A/B/C 等 2～3 个实际可行的方向，各说明收益、代价和风险，明确推荐哪项、为什么；允许人提出其他方向。

例如：A 保留方案并调整慢 case 的分块；B 对特定 shape 尝试半融合；C 先补实验确认瓶颈。实际选项由当次证据决定。

**等待与回复**：问题文档写完并通知人后，程序进入 2 分钟等待；期间持续接收消息，不启动下一轮 Stage3。

| 人的操作 | 程序行为 |
|---|---|
| 直接回复选项或具体意见 | 结束等待，把完整回复交回 Stage9；不必等满 2 分钟。 |
| 回复“等待一会儿”“请等待”等 | 固定额外等待 10 分钟；这只是等待指令，不算方案选择，也不成为 P0。 |
| 延长期间提交正式意见 | 立即结束等待，将意见完整交回 Stage9。 |
| 到期仍未给出实质回复 | 按问题文档中的推荐方案继续，由 Stage9 记录“未收到人工意见”；不能记作人工同意或人工 P0。 |

延长细则：在原 2 分钟截止时间上增加 10 分钟，同一次咨询只延长一次，最长等待 12 分钟，不进入无限等待。等待期间的多条消息完整保留；迟到回复按“主动介入”交下一次 Stage9，结合最新版本重新判断。

**重新注入 Stage9**：程序打包 **人的全部原话、选项选择和补充问题 + 原《问题文档.md》及全部选项、推荐理由 + 求助时的上下文**，重新调用 Stage9。上下文包括：需求与硬件、初始 JSON 融合库及概率、代码对应的本轮融合库和选择依据、自测材料、编译/精度/性能结果、Stage7 瓶颈分析、Stage8 搜索与修改建议、历史经验、最佳实现清单及代码/报告快照、停滞窗口和慢 case 趋势。保留已有文档的实际版本、路径、用途和阅读说明，未生成的材料明确标为缺失。

Stage9 根据完整反馈重新形成原有 P0/P1/P2 意见，其中 **人工实质建议明确列为 P0**，再交 Stage3；若人只是提问，先回答并澄清方向。不能只把人的一句话单独转给 Stage3。

两种介入都保存原话、上下文版本、等待状态、反馈包和 Stage9 最终意见，便于追溯与恢复。恢复使用原截止时间，不重新获得等待时长；人工等待和复议不增加性能迭代或 x/y 计数，同一份评测的提升/退步 ≥5% 经验不重复写入 knowledge。人工意见不直接改写 Jev 概率、成绩或最佳记录，现有失败处理、最佳选择、语义退出和迭代上限保留。

## 使用与留存

- `config.yaml` 的 `workflow.human_review.proactive_enabled` / `consultation_enabled` 分别控制主动入口和自动求助，公共配置均已开启。旧自定义配置没有此段时保持原先无人值守行为。
- `<work>/human_review/inbox/` 保存原话；`state.json` 保存处理/执行状态及停滞计数。人工方向必须有带意见编号的 P0；问题和等待不会变成修改指令。
- `<work>/human_review/<iter>/<请求编号>/` 保存问题、反馈包、证据清单及当时版本副本。咨询的 `request.json` 保存原场景、原截止时间及延期状态。
- Stage9 的实际 role、prompt、decision 留在 `knowledge/stage9/<iter>/<请求编号>/`；Stage3 在选择依据中写人工意见编号，并生成 `develop/<iter>/human_feedback.json` 落实回执。已执行仍需后续正式评测验证收益。
- 退出前的意见仍由 Stage9 处理，不能执行时写明退出原因并交 Stage10；任务结束后提交会明确拒绝，不自动重开。

**日志追溯：** `log/workflow.log` 记录问题就绪、首次读取人工回复、延期/超时、反馈打包、Stage9 裁定和 Stage3 落实。每条以请求编号、意见编号和文件路径关联，原话仅记录短摘要，全文留在 inbox；等待轮询不刷屏。CLI 提交代表原话已保存，主程序首次读取后才生成 `human_review/receipts/<意见编号>.json` 并记“已读取”，之后的“已处理”“已执行/未执行”分别记录。`--status` 查询不会冒充主程序收信。
